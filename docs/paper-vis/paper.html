What a 350M Vision-Language Model Can and Cannot Do: Three Negative Results and One Diagnostic Protocol

Kru Zeppesey
Jaume Project · ModelScope: LightNeko/Jaume
Abstract. We report three controlled negative results from building a 350M vision-language model, and one diagnostic protocol that explains all of them. (i) Looped transformers do not help: across eight task structures and four modalities, eight layers always suffice, so extra rounds repeat work rather than adding reasoning depth. (ii) A semantic vision tower cannot read: SigLIP2 and InternViT-448px both score 0.21 on a four-way text-location task, at chance, while an OCR-trained encoder (TrOCR) reaches 0.75 on the same data. (iii) Exact-match scoring hides real capability: the same model that scores 0.11 on point-localisation scores 0.50 under a distance tolerance, a 3–5× gap. The unifying protocol is a pre-flight feasibility check: before spending training compute, probe the frozen encoder with a linear classifier; if it is at chance, the information is not in the representation and no amount of training will recover it.

1. Introduction

Negative results are usually hard to publish because it is hard to prove that a failure is structural rather than a tuning accident. We collected three such results while building Jaume-Vis, a 350M parameter vision-language model on a single Ascend 910B3, and in each case we also found a measurement that turns the failure into a prediction.

The thread connecting them is simple. A representation either contains the information a task needs or it does not. If it does, training will find it given enough data; if it does not, no training helps. This sounds obvious, but it is routinely violated: we spent two rounds of tuning on an OCR task whose input representation had already destroyed the glyphs.

Contributions.

  • A depth-saturation criterion that predicts when looping cannot help, validated on eight task structures (§3).
  • Direct evidence that semantic vision towers cannot read glyphs, and that resolution is not the limiting factor (§4).
  • A demonstration that exact-match metrics can under-report capability by 3–5×, and the metric design that fixes it (§5).
  • A pre-flight protocol: linear-probe the frozen encoder before training (§6).

2. Setup

All experiments run on one Ascend 910B3 with 61 GiB HBM. The language backbone is Jaume, a 350M MoE transformer (16 layers, $d=512$, 4 experts, top-2). Vision towers are frozen unless stated. Training uses AdamW with bf16 autocast and cosine decay.

3. Depth saturation predicts that looping cannot help

3.1 The criterion

A looped transformer applies the same block repeatedly. If rounds are extra depth, a loop can only help when depth helps. We therefore measure that directly: train plain 8L and 16L models on the target task with identical data and steps.

  • 16L beats 8L by $>0.01$: the task is depth-limited, a loop has room.
  • 16L $\approx$ 8L: the task is computed in one pass; looping cannot win.

The scan costs about 0.3 GPU-hours versus 10+ for a full loop comparison.

Every task saturates at eight layers. 8-digit addition is the decisive case: it is the task the loop literature uses to argue for depth, it is learnable (0.89 exact match), it is strictly scored, and yet 8 layers match 16.

3.3 Mechanism

Inter-round relative distance decays geometrically:

$$T{=}8:\; 0.552 \to 0.363 \to 0.213 \to 0.137 \to 0.097 \to 0.074 \to 0.060$$

ratio $\approx 0.6$, and principal-subspace overlap saturates at 0.99. The loop is a contraction to a fixed point, not staged reasoning.

4. A semantic vision tower cannot read

4.1 The task

We render forms with four labelled boxes and ask which box holds a target word. A linear probe on raw pixels reaches 100%, so the render is separable.

Four-way text-location, chance 0.25. Both semantic towers are at chance; only the OCR-trained encoder reads.

4.3 It is not resolution

InternViT runs at 448px and still scores 0.21, so the failure is not the number of pixels. Tiling (2×2 and 3×3, each tile resized back to 224) moves the probe from 0.179 to 0.254, i.e. to chance. The limiting factor is the training objective, not the input bandwidth: contrastive image-text pretraining teaches global semantic matching, never glyph discrimination.

4.4 The fix is a different encoder, not more compute

TrOCR's encoder, trained on image-to-text pairs, reaches 0.75 zero-shot. With it as a second tower and a frozen Jaume backbone, a 350M model reaches 0.99 on text location and 0.89 on character reading after training.

5. Exact match under-reports capability

A point-localisation head that must reproduce an exact digit string scores 0.109. The same predictions evaluated with a $\pm1$ grid-cell tolerance score 0.504. For boxes, exact match gives 0.058 while IoU$>0.3$ gives 0.158, and a well-trained model reaches 0.347.

The gap is not cosmetic: it changed our conclusion from "localisation is broken" to "localisation works, the metric does not". Detection has used IoU for decades for exactly this reason.

A second metric pitfall. Normalised text answers must be case-folded and whitespace-collapsed before comparison. TrOCR reads "Beauty Contest" as "BEAUTY CONTEST"; scoring that as wrong measures formatting, not reading.

6. The pre-flight protocol

We propose a three-minute check before any training run:

  1. Freeze the candidate encoder.
  2. Extract features for a few hundred samples.
  3. Fit a linear classifier.
  4. If accuracy is at chance, the representation lacks the information. Change the encoder; do not train harder.

For depth, the analogous check is the 8L/16L scan. Both are cheap, both are predictive, and in our project each one replaced hours of failed training.

Two things make this possible. First, task-conditioned modulation: a gate derived from the question embedding mixes the two visual streams, and both raw streams stay in the sequence as residuals. Without it, OCR collapses from 0.89 to 0.65 when semantics are added. Second, explicit coordinate tokens: counting and pointing are decoded as grid indices rather than inferred from a feature vector.

8. Limitations

One model size, one hardware target, largely synthetic training data. The depth criterion is a negative screen: saturation rules looping out, but the absence of saturation does not guarantee a loop will help. Real-document reading remains at 0.281 and needs a dedicated OCR model in any product.

9. Conclusion

Three failures, one protocol. Representations either contain the information or they do not; a linear probe answers that question in minutes, and it predicted every one of our results before the expensive run.
