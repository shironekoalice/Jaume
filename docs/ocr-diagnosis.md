# OCR 失败的根因诊断（2026-11-10）

> 代码：scripts/ocr_diag.py、scripts/train_ocr_char.py
> 关联：docs/ocr-redesign.md（DeepSeek-OCR 借鉴方案）

## 1. 现象

OCR 三族训练 12 epoch，全部接近随机：

| 族 | 准确率 | 随机基线 |
|---|---|---|
| doc_field | 0.003 | ~0 |
| char_read | 0.100 | ~0 |
| text_locate | 0.228 | 0.250 |

loss 从 2.45 降到 0.96 就卡住不动。改了两版（整串分类 -> 字符头 -> 自回归 teacher forcing）都没有改善。

## 2. 决定性诊断：绕过 Jaume，直接测 SigLIP2

用 SigLIP2 原始特征 + 线性探针做 text_locate 四分类（最简单的那族）：

    [diag] text_locate linear probe @224px: acc = 0.194   (随机 0.250)

连视觉塔自己都做不到。这不是桥接问题，不是头设计问题，是视觉输入里根本没有可分辨的信息。

## 3. 为什么

text_locate 的图像是 320x400，每个 box 里的单词用 20px 字体渲染。缩放到 224x224 后：

- 垂直方向压缩 0.56 倍 -> 20px 字体变成约 11px
- SigLIP2 的 patch 是 16x16，一个 11px 的字连一个 patch 都填不满
- 四个 box 的单词在特征空间里几乎无法区分

## 4. 三条被排除的假设

| 假设 | 如何排除 |
|---|---|
| 桥接（projector/Jaume）太弱 | SigLIP2 原特征线性探针也只有 0.19 |
| 答案是整串分类太难 | 改成字符头、再改自回归，loss 不变 |
| 字符表不完整 | 修复后（67 类含大小写字母）仍无改善 |

## 5. 结论

OCR 在当前 224px 配置下不可解，不是模型能力问题，是信息论问题。

DeepSeek-OCR 的设计恰好对应这一点：它的 DeepEncoder 是两段式，先用窗口注意力在原生高分辨率上提特征，再压缩 token 数；而不是把整页缩到 224px 再喂给固定 16px patch 的 ViT。

## 6. 正确做法（下一步）

保持原生分辨率，压缩 token 数，而不是压缩图像。

| 方案 | 做法 | 预期 |
|---|---|---|
| A. 切片（推荐） | 把 320x400 页切成 2x2 或 3x3 块，每块单独过 SigLIP2，token 拼接 | 每块 224px 有效分辨率，词清晰可读 |
| B. 动态分辨率 | SigLIP2 支持可变 patch 数（插值位置编码），直接喂 448/512 | 已验证 320 会崩（NPU 算子），448 风险更高 |
| C. 两段式编码器 | 照搬 DeepSeek-OCR：卷积下采样 + 局部注意力 | 改动大，但最接近原论文 |

推荐 A：切片是纯工程方案，不需要改模型结构，且天然适配文档/UI 多块布局的场景——正好是你要做的 UI 模型需要的。

## 6b. 切片验证：推翻了"分辨率不足"假设（2026-11-10）

按第 6 节的方案 A 实现切片后，用**同样的线性探针**再测：

| 配置 | 准确率 | 说明 |
|---|---|---|
| 整图 224px（1 tile） | 0.179 | 原始基线 |
| **2x2 切片**（每块 184x230 -> 224） | **0.254** | 信息保留甚至放大 |
| **3x3 切片**（每块 122x153 -> 224） | **0.254** | 同上 |

切片把准确率从 0.179 提到 0.254，**但仍等于随机（0.25）**。

### 修正结论：不是分辨率，是 SigLIP2 的能力边界

每块放大到 224 后，字形信息**完整保留**（甚至比原图更清晰），
SigLIP2 仍然无法区分四个不同的单词。这说明：

**SigLIP2 不具备细粒度字形判别能力。**

原因是它的训练目标：图文对比学习要求"整图匹配整句"，
从未被要求区分 ALPHA / OMEGA 这类字形级差异。这是 CLIP 家族
的已知局限，不是我们的实现问题。

### 能力边界（重要）

| 能力 | SigLIP2 | 证据 |
|---|---|---|
| 语义理解（物体/场景/属性） | 强 | 合成套件 0.95、CIFAR 0.80 |
| 计数、空间、比较 | 强 | 均 > 0.8 |
| **细粒度字形（OCR）** | **弱** | 切片后仍为随机 |

### 修正后的 OCR 方案

切片不够，需要**换视觉塔**：

1. **专用 OCR 视觉塔**：如 DeepSeek-OCR 的 DeepEncoder（SAM+CLIP，
   其 CLIP 在 OCR 数据上继续训练过）；
2. **对 SigLIP2 做 OCR 领域继续训练**：用大量文本图像对微调视觉塔，
   让它学会字形判别——成本高但可行；
3. **纯 OCR 模型路线**：UI 场景直接接 PaddleOCR / TrOCR 这类专用模型，
   把 Jaume 用在"理解层"而非"识别层"。

**推荐 3 用于产品，2 用于研究。** Jaume 的定位应该是
"看懂图里的语义"，而不是"逐字识别"——后者交给专用模型更划算。

## 6c. 最终裁决：OCR 必须用 OCR 专用视觉塔（2026-11-10）

在同一个 text_locate 任务上横向测了三个视觉塔，全部零样本 / 冻结特征：

| 视觉塔 | 参数 | 分辨率 | 准确率 | 结论 |
|---|---|---|---|---|
| SigLIP2-base | 93M | 224 | 0.210 | 随机水平 |
| InternViT-300M | 304M | **448** | 0.209 | 随机水平 |
| **TrOCR-base** | 334M | 384 | **0.750** | **3x 随机，可用** |

关键点：

1. **InternViT 的 448px 也没救**。这说明"分辨率"不是主因，
   训练目标才是——InternViT 也是图文语义对齐，不是字符识别。
2. **TrOCR 是唯一能读字的**，因为它的训练目标就是"图像 -> 文字序列"。
   即使零样本、即使有错字（SIGMA->SIGNA、ALPHA->APHA），
   它仍然能在四选一里定位到正确的 box。
3. 之前担心的"是不是评估代码有 bug"已排除：
   - 渲染本身完全可分（原始像素线性探针 100%）
   - 按 box 池化的正确探针仍是 0.21

### 最终架构建议：双塔



- 通用识图：SigLIP2 单独就够（0.95 合成 / 80% CIFAR）
- OCR/UI：TrOCR 提文字 + 位置，Jaume 做语义理解
- 这正是主流文档 VLM 的做法（识别与理解分离）

### 产品建议

**不要试图让语义视觉塔学会 OCR。** 这是两条不同的技术路线：

- 识别层：TrOCR / PaddleOCR / DeepSeek-OCR，成熟且便宜
- 理解层：SigLIP2 + Jaume，这是我们的优势

**Jaume 的定位应该是"看懂"，不是"看清"。**

## 7. 对 Jev / UI 模型的指导

1. 永远不要在 224px 上做 OCR。这是本轮最硬的教训。
2. 视觉塔的 patch 尺寸（16px）决定了最小可读字号：字号 < 2x patch 就不可读。
   - patch16 @ 224px：最小可读约 32px（原图坐标下按缩放比折算）
   - UI 常见 12-14px 字号 -> 需要原生分辨率 + 切片，或 patch8 的小 patch 模型
3. 先做信息论可行性检查（像本轮的线性探针），再投入训练算力。这个检查只花 3 分钟，却省下了几小时无效训练。
