## 1. 实现要点（当前最佳实践）

1. **缓存 GQA 展开前的 KV**：只存  个头，而非 ，
   内存正好省一半（实测 2.8 MiB / 16 层 / 128 位置）。
2. **RoPE 在写入时应用**：新 token 的 K 用**绝对位置**（past_len+i）旋转后
   存入，读取时无需再旋转 —— 这是让每步 O(1) 而非 O(T) 的关键。
3. **静态预分配 + 写游标**：一次分配 ，
   原地写入，避免每步重新分配造成的 O(T) 拷贝和显存碎片。
4. **显式 opt-in**： 逐位复现旧行为，所有历史实验可比。
5. **repeat_kv 在缓存路径返回视图**（），避免每步复制整个历史。

| 操作 | 单次耗时 |

**T=1 只比 T=64 快 22%。** 也就是说这个模型在这个硬件上
**是延迟受限（latency-bound），不是计算受限**：

- 16 层 × 每层 ~6 个算子 ≈ 100 次 kernel 启动/同步
- attention 的 O(T²) 计算只占总时间的约 20%
- 缓存省下的那部分，被固定的算子启动开销完全淹没

## 4. 结论与适用范围

**KV cache 在 350M / 单序列 / 短上下文上收益接近 0，但它仍然是必需的：**

1. **长上下文**：当 T 从 64 涨到 4096，attention 占比从 20% 升到主导，
   缓存收益随之线性放大。T=4096 时缓存理论加速 >10x。
2. **更大模型**：Jev 若到 1-3B，计算/启动比上升，缓存收益随之出现。
3. **batch 推理**：batch>1 时计算量线性增长，固定开销被摊薄，
   缓存的相对收益上升。
4. **流式 UI 理解**：连续帧共享前缀，缓存的增量特性天然契合。

**不要用小模型短序列的 1.0x 否定 KV cache。** 正确的判断标准是
"attention 占比"—— 这个模型现在只有 20%，所以是 1.0x。

## 5. 对 Jev 的直接指导

- KV cache 必须**从第一天就内置**（本实现可直接复用）；
- 但 Jev 的性能目标要**按延迟/算子启动开销**来评估，而不只是 FLOPs；
- 若要提升小模型的解码速度，比 KV cache 更有效的是：
  **算子融合**（减少 kernel 启动次数）和 **CUDA/NPU Graph**（消除启动开销）。
  这是 350M 尺度上真正的瓶颈。

## 6. 后续可做

| 优化 | 预期收益（350M） |
|---|---|
| NPU Graph 捕获整个 decode step | 消除 ~100 次启动开销，可能 2-3x |
| 算子融合（RMSNorm+Linear、QKV 合并） | 减少 30-40% 算子数 |
| 静态 shape + 固定 batch decode | 配合 Graph 必需 |
| PagedAttention / 连续批处理 | batch>1 时显著 |
