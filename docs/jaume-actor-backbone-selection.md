> 日期：2026-11-20。状态：选型完成，三个基座在真实 ScreenSpot 上实测。

## 0. 结论

**结论分三层，第三层是对第一层的修正 —— 三层都要看。**

### 0.1 基座选型（真实 ScreenSpot，冻结特征 + 线性探针，held-out）

| 基座 | 参数量 | 形态 | AUROC | 候选打分 top-1 | 地板 | 每 crop 耗时 |
|---|---|---|---|---|---|---|
| **SigLIP2-base** | **93M** | 双塔（视觉+文本，无 LM） | 0.8991 | **0.8500** | 0.1667 | **44 ms** |
| Qwen3-VL-2B | 2B | VLM | **0.9472** | 0.8056 | 0.1667 | 481 ms |
| Qwen2-VL-2B | 2B | VLM（上一代） | 0.9046 | 0.6667 | 0.1667 | 580 ms |

**在「候选靠外观区分」的任务上，SigLIP2 用 1/22 的参数拿到更高的 top-1，
且每 crop 快 11 倍。**

### 0.2 指令条件化（真实干扰项，seeclick，held-out）

| head | 参数 | held-out top-1 | 地板 |
|---|---|---|---|
| 线性探针（指令仅拼接） | 1.5K | 0.1846 | 0.1667 |
| **门控头（指令调制视觉）** | 2.4M | **0.6483** | 0.1667 |
| **门控头但去掉指令（对照）** | 2.4M | 0.1827 | 0.1667 |

**门控 +46 个点；去掉指令立刻掉回地板。** 对照组证明这是条件化的功劳，
不是参数量的功劳。

### 0.3 ⚠️ 修正：真 DOM 需要 OCR，SigLIP2 没有

把门控头接到**真实 DOM 候选集**上，top-1 = **0.0000**，而且**无指令对照组
也是 0.0000**。根因用最小复现定位：**SigLIP2 读不出按钮上的文字**
（渲染六个标签只对 1 个）—— 它是图文对齐模型，不是 OCR 模型。

真 DOM 上的四条路线（同一批页面、同样的候选集）：

| 方案 | top-1 | 地板 | 延迟/决策 |
|---|---|---|---|
| SigLIP2 + 训练过的门控头 | 0.0000 | 0.125 | 9.6 ms（只有头） |
| Qwen3-VL-2B，K 张裁剪塞进一个 prompt | 0.2857 | 0.125 | **16530 ms** |
| TrOCR-small + 字符串匹配 | 0.1818 | 0.056 | 1659 ms/页 |
| **Qwen3-VL-2B，一张裁剪一次 + 匹配** | **1.0000** | 0.125 | 862 ms/crop |

**能用的结构是两阶段**：定位（一次前向）→ 每张裁剪单独读字（OCR）→ 匹配。

**并且「一次前向塞 K 张图」被证伪**：同样的模型、同样的候选集，
一次 8 张图是 0.2857（无指令对照 0.1429 = 地板）、16530 ms；
8 次单图是 1.0000、862 ms/crop。
VLM 在多图 prompt 里会丢失逐图对应关系。

### 0.4 这次选型学到的最重要的一课

第一版候选集用**随机框**当干扰项，结果「去掉指令的对照组」也拿到 1.0000 ——
**指令根本没用上**，任务退化成「这裁剪是不是 UI 元素」。换成**真实 UI 元素**
当干扰项后，结论才成立。而换成真实 DOM 后，**又推翻了第一层的选型结论**。

> **任何 grounding 基准都必须有「去掉指令的对照组」。**
> 而且**候选集的构造方式会决定基准测什么** —— 随机框测的是「像不像 UI 元素」，
> 真实 DOM 测的是「读不读得出标签」。同一个模型在两者上的排名可以完全相反。

### 0.5 推理布局的代价（Qwen3-VL-2B）

| 布局 | 准确率 | 延迟 | 每次前向的图数 |
|---|---|---|---|
| 截图 + K 候选裁剪，读字母 logit | 0.480（地板 0.167） | **8998 ms** | 7 |
| 只截图 + 坐标回归 | 0.140 | 12329 ms | 1 |

而不是「把 2B VLM 塞进决策环」。**

## 1. 为什么不能用合成基准选型

`docs/jaume-actor-prototype.md` 的合成 UI 基准上，**所有变体都是 1.000**，
包括「去掉整屏」「去掉元素裁剪」。一个所有配置都满分的基准**测不出任何差别**，
用来选基座只会得到「随便哪个都行」的无效结论。

所以选型必须换数据。换到 **ScreenSpot**（SeeClick 出品，Apache-2.0）：
1272 张真实截图，覆盖 iOS / Android / macOS / Windows / Web，
每条 = 截图 + 自然语言指令 + 目标元素的标注框。

```bash
# 数据：ModelScope（本机 HuggingFace 不可达）
python fetch_models.py                                   # 基座权重
snapshot_download("rootsautomation/ScreenSpot", repo_type="dataset")
```

## 2. 评测协议

### 2.1 动作空间：候选打分，不是坐标回归

公开的 ScreenSpot 榜单全是**坐标回归**（直接预测框），和本项目的动作空间
（打分候选集 + argmax）不同。所以每个基座都在**项目真正要用的动作空间**里测：

```
候选集 = 目标框 + (K-1) 个从同一张截图里采样的干扰框
干扰框面积与目标框匹配（±60%），所以答案不能靠「挑最大的框」猜出来
K=6，地板 = 1/6 = 0.1667
```

### 2.2 两种读出方式，缺一不可

| 读出 | 做法 | 回答什么问题 |
|---|---|---|
| **零样本单次前向** | VLM 把截图和候选裁剪一起喂进去，选项标 A/B/C…，读**字母 token 的 logit**（不解码） | 不训练能不能用？ |
| **线性探针（held-out）** | 冻结编码器，接一个线性头，在 **70% 训练 / 30% 测试** 的划分上训 | 表征里有没有信息？训练能挖出多少？ |

两者的差距是关键信息：它说明**骨干的知识有多少能被便宜的头读到**，
因而决定 actor 需要多少训练。

### 2.3 探针的负例来自同一张截图

每个样本的正例是目标裁剪，负例是**同一张截图的其他候选裁剪**。
这样探针不能靠「这张截图有个红色按钮」取胜，必须真的把裁剪和指令对上。

## 3. 两个必须记录的修正

### 3.1 探针最初在训练集上评估

第一版探针在同一批截图上训练和评估，报出 AUROC 0.9916 / top-1 0.9500 ——
**那是拟合度，不是泛化度**。仓库早就被这个问题咬过（README：「STS 分数来自
有 train/eval 重叠的历史流程，只能当流程检查，不能当 held-out 结果」）。

加上 70/30 的截图级划分后：

| 基座 | 拟合版 top-1 | **held-out top-1** |
|---|---|---|
| SigLIP2 | 0.835 | 0.850（**没掉**，1536 维上只有 2 个参数，过拟合不了） |
| Qwen3-VL-2B | 0.950 | 0.806（掉 0.14，2048 维 × 2B 骨干，过拟合了） |
| Qwen2-VL-2B | 0.850 | 0.667（掉 0.18） |

**VLM 骨干的探针会过拟合，纯视觉塔不会** —— 因为 VLM 的特征维度更高、
分布更复杂，一个线性头在上面能找到只在训练图上成立的捷径。

### 3.2 零样本读出低于随机地板

SigLIP2 的零样本余弦相似度（crop 嵌入 · 指令嵌入）在 ScreenSpot 上是
**0.083**，而地板是 0.167 —— **比随机还差**。

但同一批特征上的探针是 0.850。**信息在特征里，是读出方式错了。**
这不是矛盾：SigLIP2 是图文对齐模型，不是 referring-expression grounding
专家，直接拿余弦相似度去排候选本来就问错了问题。

> **这条是本轮最实用的一条**：不要用零样本分数判断一个骨干「行不行」。
> 零样本差只说明默认读出不对，不说明表征里没有信息。
> 探针才是判断表征的便宜手段（仓库 README 的第一条经验）。

## 4. 推理布局的代价（Qwen3-VL-2B，50 样本）

| 布局 | 做法 | 准确率 | 延迟 | 每次前向的图数 |
|---|---|---|---|---|
| **L1 全提示** | 截图 + K 张候选裁剪 + 指令，一次前向读字母 logit | top-1 **0.480**（地板 0.167） | **8998 ms** | 7 |
| **L2 只截图 + 坐标回归** | 截图 + 指令，生成框 | regression **0.140** | 12329 ms | 1 |

**L2 的 0.140 是负结果**：Qwen3-VL-2B 在这个提示下几乎不产生可用的框
（解析成功率 100%，但框落在目标内只有 14%）。这与公开榜单上 Qwen 系列的
表现差距很大，说明**提示词格式对这个模型很敏感**，不能拿一个随手写的提示
就下结论。

**L1 的 8998 ms 是致命的**：一次决策要过 7 张 224px 图的视觉塔。
这对浏览器操作勉强可接受（人操作也就几秒一次），但对游戏完全不可用。

**这条直接指向架构**：既然 SigLIP2 的探针 top-1 就有 0.850，且**每 crop
只要 44 ms**，那么正确做法是

```
冻结 SigLIP2（93M）
  → 每个候选一次编码（44 ms/crop）
  → 训练一个轻量打分头（状态内 softmax CE）
  → argmax
```

而不是把 2B 的 VLM 整个塞进决策环。

## 5. 决定性实验：指令条件化是必需的

前面所有数字都用「随机框」当干扰项。换成**真实干扰项**（同一截图里的其他真实
UI 元素）后，结论完全变了 —— 这本身是本轮最重要的一次修正。

### 5.1 随机干扰项让指令变得无关

在 ScreenSpot 的**随机框**候选集上（300 样本，K=6）：

| head | held-out top-1 | 地板 |
|---|---|---|
| 线性探针（指令仅拼接） | 0.8889 | 0.1667 |
| 门控头（指令调制视觉） | **1.0000** | 0.1667 |
| **门控头但去掉指令（对照）** | **1.0000** | 0.1667 |

**对照组也满分 → 指令完全没被用到。** 原因很清楚：随机框落在**纯背景**上，
而 GT 是真实 UI 元素（文字或图标）。于是任务退化成「这个裁剪是不是 UI 元素」，
根本不是 grounding。

> **这条是本轮最贵的教训**：一个让对照组也满分的基准，会把「模型没在学目标任务」
> 伪装成「模型学会了目标任务」。**任何 grounding 基准都必须有「去掉指令的对照组」。**

### 5.2 真实干扰项：门控的收益是 +46 个点

改用 seeclick 的**真实元素**当候选（同一截图里的其他真实 UI 元素，
400 张截图 → 2586 个样本，K=6，按截图 70/30 划分）：

| head | 参数 | held-out top-1 | 地板 |
|---|---|---|---|
| 线性探针（指令拼接） | 1.5K | 0.1846 | 0.1667 |
| **门控头（指令调制视觉）** | 2.4M | **0.6483** | 0.1667 |
| **门控头但去掉指令（对照）** | 2.4M | 0.1827 | 0.1667 |

三条结论，每条都由对照支撑：

1. **指令条件化是必需的。** 门控头 0.6483，线性拼接 0.1846（≈地板）。
   把指令从「拼接」改成「调制」，涨 **+46 个点**。
2. **对照组确认了这是条件化的功劳，不是参数量的功劳。** 同样的 2.4M 参数，
   去掉指令就掉到 0.1827（地板）。门控头在没有指令时无法区分候选。
3. **这与仓库既有的结论同构。** `docs/vlm-dual-tower-spec.md` 在双塔视觉模型上
   测到「去掉问题条件化门控，OCR 均值从 0.887 掉到 0.65」。
   这次在**候选打分**这个新动作空间上独立复现了同一个机制。

### 5.3 门控的具体形式

```
v  = SigLIP2_image(crop)                      768 维（冻结）
t  = SigLIP2_text(instruction)                768 维（冻结）
t' = W_text · t                              投影到视觉空间（可训练）
g  = sigmoid(W_gate · t')                    门控（可训练）
fused = v * (1 + g) + t'                     残差保留原始视觉流
score = MLP([fused ; v ; t' ; proj(box)])    候选打分（可训练）
```

* 残差（`v` 保留原始流）很重要：仓库实测过去掉任一条流都会塌缩
  （OCR 0.887 → 0.65）。
* **两塔不同维**这件事在这个 checkpoint 上要小心：config 说两塔都是 768，
  但实测的池化输出也是 768/768，**而 `get_image_features` 不存在**
  （旧 config 格式，必须手动跑 `vision_model` / `text_model`）。
  仓库 `docs/vision-competence.md` 记过同一件事。

## 6. 选型结论与架构含义

### 6.0 ⚠️ 重要修正：选型结论只对「构造的候选集」成立

把训练好的门控头接到**真实 DOM 候选集**上（`eval_browser_gated.py`，
真 Chrome，候选 = 页面真实的可点击元素，K=18），结果是：

| head | held-out top-1 | 无指令对照组 | 地板 |
|---|---|---|---|
| 门控头（SigLIP2 + 训练过的打分头） | **0.0000** | **0.0000** | 0.0556 |

**两者都是 0** —— 不是 head 不行，是**特征不行**。

诊断（渲染文字的最小复现）：把 "Action 0"… "Delete" 六个按钮渲染成图，
裁剪后与对应指令算 SigLIP2 的余弦相似度：

```
crop              click Action 0  click Action 1  ...  click Delete
Action 0              0.000         -0.010         ...      -0.051
Action 1              0.003         -0.002         ...      -0.035
...
argmax per instruction: 6 个里只对 1 个
```

**SigLIP2 读不出按钮上的文字。** 它是图文对齐模型，不是 OCR 模型。
而真实 DOM 候选集里，元素的**身份就是它的标签** —— 没有别的特征可用。

于是真实-DOM grounding 需要**两种能力**：

| 能力 | SigLIP2 | VLM（Qwen3-VL 等） |
|---|---|---|
| (1) 读出元素上的文字（OCR） | **没有** | 有 |
| (2) 把文字和指令对上（对齐） | 有 | 有 |

**所以 §6.1 的选型结论要加一个限定条件**：

> **SigLIP2 更适合「元素有独特外观」的候选集**（合成 UI、图标、
> 空间关系），**不适合「元素靠文字区分」的候选集**（真实 DOM）。
>
> 真 DOM 任务必须用有 OCR 能力的骨干，或者给 SigLIP2 配一个 OCR 通路
> （仓库的 `docs/vlm-dual-tower-spec.md` 正好是双塔 + TrOCR 的配方：
> SigLIP2 管语义、TrOCR 管字形）。

**这条修正也解释了 §4.3 的真浏览器 1.0000**：那个用的是仓库自有的
`UIActor`（小 CNN），它靠**位置框**而不是读文字来区分候选 ——
合成页面上「蓝色的圆」和「红色的方块」靠外观就能分，不需要 OCR。

### 6.0.1 Qwen3-VL 在真 DOM 上也不灵（而且慢 400 倍）

用同样的真 DOM 页面、同样的一次前向读字母 logit（`browser_dom_backbones.py`，
K=8 候选，14 条指令）：

| 骨干 | top-1 | 无指令对照 | 地板 | text 类 | visual 类 | 延迟/决策 |
|---|---|---|---|---|---|---|
| SigLIP2 + 训练过的门控头 | 0.0000 | 0.0000 | 0.125 | 0.000 | 0.000 | 9.6 ms* |
| **Qwen3-VL-2B（零样本，全 prompt）** | **0.2857** | 0.1429 | 0.125 | 0.1429 | **0.4286** | **16530 ms** |

\* 只有 head 的时间，不含视觉塔。

两条结论：

1. **Qwen3-VL 零样本的多图 prompt 也不行**（0.2857 vs 地板 0.125）。
   它的无指令对照是 0.1429（正好是地板），所以它**确实在用指令**，
   但远不如一次读一张图（1.0000）。
   它在 **visual 类指令上有 0.4286**（看得懂颜色），在 **text 类上只有 0.1429**
   —— 有 OCR 能力，但在这个「一次前向塞 9 张图」的提示格式下用不出来。

2. **延迟 16.5 秒/决策**，比 SigLIP2 路线慢 1700 倍。
   原因：一次前向要过 9 张 224px 图（1 整屏 + 8 裁剪），
   而 VLM 的图像 token 数是 SigLIP2 的数倍。

### 6.0.3 真 DOM 上的四种方案（决定性对照）

在**同一批真实 DOM 页面**（真 Chrome，候选 = 页面真实的可点击元素，K=8–18）：

| 方案 | top-1 | 地板 | 延迟 | 关键数字 |
|---|---|---|---|---|
| SigLIP2 + 训练过的门控头 | **0.0000** | 0.125 | 9.6 ms（只有头） | 无指令对照也是 **0.0000** |
| Qwen3-VL-2B，K 张裁剪塞进一个 prompt | 0.2857 | 0.125 | **16530 ms** | 无指令对照 0.1429（=地板）；text 类 0.1429、visual 类 0.4286 |
| TrOCR-small + 字符串匹配 | 0.1818 | 0.056 | 1659 ms/页 | OCR 读出的是垃圾："Submit"→"TABLE"、"Action 3"→":" |
| **Qwen3-VL-2B，一张裁剪一次** | **1.0000** | 0.125 | **862 ms/crop** | OCR 精确匹配率 **0.875** |

**最后一行是能用的方案**，而且它验证了「两阶段」这个结构：

```
阶段 1  定位   候选框（DOM 给，或训练一个检测器）
阶段 2  确认   每张裁剪单独读一次文字 → 与指令做字符串匹配
```

阶段 2 之所以有效，是因为**一次一张图**时 VLM 的 OCR 能力完全正常
（精确匹配率 0.875），而**一次 K 张图**时它既慢 19 倍又做不对
（0.2857，无指令对照 0.1429 = 地板 —— 它在用指令，但效率极低）。

> **重要的一条测量教训**：这个 VLM checkpoint 的 `generate` 会把整个
> 聊天提示回显出来。第一次测时 OCR 精确匹配率是 **0.0000**，而任务 top-1
> 却是 1.0000 —— 矛盾的原因就是回显的提示词里包含了指令文字，
> 让「包含关系匹配」成功了。**必须先在 assistant 标记处截断再测**，
> 否则精确匹配指标会骗人。

### 6.0.4 三条能力结论

| 能力 | SigLIP2 | TrOCR-small | Qwen3-VL-2B |
|---|---|---|---|
| 读按钮上的文字（OCR） | **不能**（6 个只对 1 个） | **不能**（印刷体域外） | **能**（精确匹配 0.875） |
| 把图和文字对上（对齐） | 能 | — | 能 |
| 一次 K 张图 | 快（44 ms/crop） | — | 慢且不准（16530 ms，0.2857） |

**所以最终的骨干结论是分层的**：

| 用途 | 用什么 | 证据 |
|---|---|---|
| 候选集靠**外观**区分（图标、颜色、空间关系） | SigLIP2-base 93M | top-1 0.850 vs 0.806，参数少 22 倍，每 crop 快 11 倍 |
| 候选集靠**文字**区分（真实 DOM） | 需要 OCR 能力：VLM | OCR 精确匹配 0.875，任务 top-1 1.0000 |
| 两者都要 | **双通路**：SigLIP2 管语义 + OCR 管字形 | 仓库 `docs/vlm-dual-tower-spec.md` 已经做过这个配方（SigLIP2 + TrOCR） |

### 6.0.5 「一次前向塞 K 张图」不可行

这是本轮最贵的一个否定结论，量化如下：

| 做法 | 每决策延迟 | top-1 |
|---|---|---|
| K 张图塞进一个 prompt（Qwen3-VL-2B） | 16530 ms | 0.2857 |
| K 次单图调用 + 字符串匹配（Qwen3-VL-2B） | 862 ms × K | **1.0000** |

**同样的模型、同样的候选集、同样的动作空间**，
只是把「一次 8 张图」换成「8 次单图」，结果从随机变成满分。

原因：VLM 在多图 prompt 里会丢失逐图的对应关系（哪个候选对应哪个选项），
而单独读每张图时它是可靠的。**这个结论对任何「让模型在一堆候选里选」的
设计都成立** —— 不要把候选做成多图 prompt，要一个一个看。

### 6.0.6 选型结论的适用范围

| 结论 | 适用范围 |
|---|---|
| SigLIP2 优于 2B VLM | **仅限不依赖读文字的候选集** |
| 门控头带来 +46 个点 | 仅限构造候选集（seeclick 真实元素干扰项） |
| 真 DOM 需要 OCR 能力 | 通用，**已由四条独立路线交叉验证** |

### 6.1 基座选型（限定在「不依赖读文字」的候选集上）

| 判据 | SigLIP2-base | Qwen3-VL-2B |
|---|---|---|
| held-out 候选打分 top-1 | **0.850** | 0.806 |
| 参数量 | **93M** | 2B（21.5×） |
| 每 crop 编码耗时 | **44 ms** | 481 ms（10.9×） |
| 零样本单次前向 | 不适用（需训练读出头） | 0.500，但 8.7 s/次 |
| 训练需求 | 需要（读出头） | 需要（读出头），且特征更易过拟合 |
| 仓库已有配方 | **有**（`vlm-dual-tower-spec.md` 已验证 SigLIP2 冻结 + projector） | 无 |

**决定性理由是延迟和参数量**，而不是精度。93M 的模型能在 44 ms 内编完一个
候选裁剪，2B 的 VLM 要 481 ms —— 在一个 60 Hz 的控制环里，480 ms 的单次编码
就已经出局了。

### 6.2 SigLIP2 的短板，以及门控如何补上它

SigLIP2 是**双塔**：crop 嵌入和指令嵌入是**并列**的，线性探针只能用拼接，
所以**指令没有真正参与视觉编码**。

§5 的实验正好量化了这个短板，并给出了修法：

| 读出方式 | 真实干扰项下的 held-out top-1 |
|---|---|
| 线性探针（指令仅拼接） | 0.1846（≈地板） |
| **门控头（指令调制视觉）** | **0.6483** |

**所以选型结论不是「SigLIP2 更好」，而是「SigLIP2 + 一个指令条件化的门控
更好」**。门控就是仓库 `docs/vlm-dual-tower-spec.md` 里那个
**问题条件化门控**，在这里被独立复现到了一个新的动作空间上。

完整结构：

```
SigLIP2-image(crop)  ──► v (768, 冻结) ──┐
                                          ├─► fused = v*(1+g) + t' ──► 打分头
SigLIP2-text(instr)  ──► t (768, 冻结) ──► t' = W·t, g = σ(W_g·t')  （可训练 2.4M）
box                  ──► proj(box) ──────┘
```
