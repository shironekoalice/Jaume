## 0. 一句话结论

**可以，但架构上有一个硬性设计约束：决策必须是「一次前向 + 打分 + argmax」，
不能是自回归解码；而且小模型该做「感知」，不该学「规划」。**
本文用两个原型验证了这个约束：浏览器侧（候选元素打分）合成 held-out top-1 **1.000**、
**真浏览器 grounding 1.000**；游戏侧（像素闭环控制）用「小感知模型 + 符号规划器」
闭环成功率 **1.000**（3/3 seed，最差 seed 也是 1.000），单次决策 **9.85 ms**，
对比「学出来的策略网络」的 0.710。

三条可迁移的架构结论：

1. **一次前向出决策。** 仓库自己的实测：350M 模型 T=1 解码 154 ms，
   输出动作文本要 1.5 秒 —— 实时控制环用不了。
2. **规划交给确定性求解器。** 学出来的策略网络把规划内化到权重里，
   内化的规划是错的（0.710 vs 1.000）。
3. **任何能绕过视觉的输入通路都会诱发捷径解。** 坐标通道、过大初始 logit
   尺度都会让模型「不看图」而塌缩（详见 §3.6–3.8）。

## 1. 为什么「不用自回归解码」是硬约束

`README.md` 的基础设施表里有一条实测：**350M 模型 T=1 解码 154 ms**。
这意味着输出 10 个 token 的动作文本就要 1.5 秒。游戏是 15–60 Hz 的控制环，
浏览器点击虽然慢一点但也远不到 1.5 秒。

所以本方向的推理规则被固定为：

```
一帧 / 一个候选集 → 一次前向 → 对候选打分 → argmax → 结束
```

三条约束贯穿所有实验：

| 约束 | 依据 |
|---|---|
| 一次前向出决策，不解码字符串 | 154 ms/token 的实测延迟；公开对照 PlayJev 0.8B 也是 43 ms/步单次前向 |
| 用**状态内 softmax CE**，不用逐项 BCE/MSE | `planning-report.md` §4.7：BCE 塌缩到全负基线，MSE 被尺度主导 |
| 动作空间 = **有限候选集**，不是自由坐标 | 公开结论：候选打分比坐标回归高 5–20 个点；且坐标回归在 1B 尺度上误差不可控 |

## 2. 浏览器侧：候选元素打分

### 2.1 任务设计（两个版本）

**v1（平凡，被否）**：指令 = 颜色 + 形状 + 位置带 + 列，6 个候选。
所有变体（含「去掉整屏」）都到 1.000 —— 说明这个基准测不出任何东西，
因为单看元素裁剪图就能答对。**保留这个负结果：它证明了「消融到 1.000」是基准设计的失败信号，不是模型的成功信号。**

**v2（难版，最终采用）**：屏幕上放置 **decoy twin** —— 与目标同色同形、只有位置不同的干扰项。
因此指令必须把局部外观特征和全局位置特征结合起来才能唯一确定答案。

| 对照 | 值 | 含义 |
|---|---|---|
| random | 0.1667 | 1/6 |
| heuristic（只匹配颜色+形状） | **0.3475** | 解不了 twin，是地板不是目标 |
| oracle（颜色+形状+位置） | 1.0000 | 按构造即满 |

### 2.2 结果（3000 训练 / 800 held-out，20 epoch，0.26M 参数）

| 变体 | 参数 | top-1 |
|---|---|---|
| full（crop + 整屏 + box） | 0.258M | **1.0000** |
| no_screen（去掉整屏） | 0.108M | **1.0000** |
| no_crop（去掉元素裁剪） | 0.177M | **1.0000** |
| **no_box（去掉位置框）** | 0.258M | **0.5480** |
| text_only | 0.026M | 0.1660（= 随机） |

**读法**：

1. **位置框是唯一不可替代的输入**。去掉 box 掉到 0.548，接近 heuristic 地板 —— 因为
   twin 的外观完全一样，唯一区分信息就是位置。这正是 v2 基准想测的东西，它做到了。
2. 整屏和裁剪图**互相冗余**：去掉任一个都还是 1.000。这说明在这个合成任务上，
   位置坐标 + 元素外观已经足够；真实页面上整屏会提供裁剪图没有的上下文
   （例如「这个按钮在页脚还是正文」），所以工程上仍然建议保留整屏输入。
3. `text_only` 精确等于随机 1/6，证明损失函数没有留下「答案先验」的漏洞
   —— 这正是 §4.7 那个 BCE 塌缩问题在 CE 下不存在的样子。

### 2.3 真实浏览器验证（Playwright + 系统 Chrome）

`eval_browser_ui.py` 从**真实 DOM** 读取候选元素的包围盒，从**真实截图**取像素
（视口 1280×900 真实截图，再缩放到 128×128 给模型），喂给训练好的 actor。

| 模板 | 准确率 | 样本数 |
|---|---|---|
| buttons（彩色文字按钮） | **1.000** | 8 |
| cards（纯色无字矩形） | **1.000** | 6 |
| mixed（不同布局） | **1.000** | 6 |
| **合计（开放环 grounding）** | **1.0000** | **20** |

**闭环控制**（`browser_loop.py`）：点完之后页面真的变了，再选下一个。

| 任务 | 结果 |
|---|---|
| 单步：选对一个控件并真的点下去（4 种颜色） | 4/4 |
| 两步：先点 Continue，第二步的目标元素**此时才出现在 DOM 里** | 2/2（两轮都选对） |
| **合计** | **1.0000（6/6）** |

**这条链路里踩了三个 bug，每一个都会把分数打下来，值得记下来：**

1. **视口设成了 128×128**（模型的输入尺寸），但页面内容需要 1280 宽，
   DOM 坐标到了 y=677，而截图只有 128 高 —— 所有裁剪都是空白，
   真浏览器准确率被压到 **0.200**。修法：真实尺寸截图 + 缩放，
   DOM 框按同一比例换算。
2. **gold 标注只看 class**。card 模板的颜色写在 inline style 里，
   class 里没有颜色 —— 于是 cards 模板恒为 0.000，
   而模型其实选对了。修法：同时查 `getComputedStyle().backgroundColor`。
3. **card 模板压根没设颜色**（`items` 声明了颜色，HTML 里漏了），
   背景是 `rgba(0,0,0,0)`。修法：补上。

三个 bug 叠加，最终从 0.200 修到 1.000。**记录这条是因为：如果只报中间那个
0.200，会得出「合成基准 1.000 是假象、真浏览器上不可用」的错误结论。**

### 2.4 UI actor 的多 seed 稳定性

合成 UI 的 1.000 最初也是单 seed。因为 §3.6 记录了迷宫检测器的 bimodal，
UI 侧用同样的标准重测（`ui_multiseed.py`，3 seeds，6000 训练 / 1500 测试）：

| 变体 | 参数 | top-1 均值 | **top-1 最差 seed** |
|---|---|---|---|
| full（crop + 整屏 + box） | 0.258M | 1.0000 | **1.0000** |
| no_screen（去掉整屏） | 0.108M | 1.0000 | **1.0000** |
| no_crop（去掉元素裁剪） | 0.177M | 1.0000 | **1.0000** |
| **no_box（去掉位置框）** | 0.258M | 0.5418 | **0.5387** |
| text_only | 0.026M | 0.1573 | 0.1573（随机基线 1/6 = 0.1667，有限样本内无差异） |

UI 侧**没有**出现迷宫那样的 bimodal —— 3/3 seed 全 1.0000。
这与架构差异一致：UI actor 的候选输入是「裁剪图 + 相对候选的位置框」，
**没有任何与像素无关的捷径**（没有坐标通道，位置框不指向答案），
所以不会诱发 §3.7 那类塌缩。

## 3. 游戏侧：像素闭环控制

### 3.1 任务

8×8 随机墙迷宫，起点终点随机。agent 是蓝色圆，goal 是绿色**菱形**。
每 tick 看一帧像素，选 4 个方向之一，走满预算内到 goal 算成功。
oracle = 精确 BFS 最短路（成功率 1.000，平均 6.0 tick）。

### 3.2 走过的弯路（每一步都有数据支撑）

| 版本 | 做法 | 闭环成功率 | 为什么失败 |
|---|---|---|---|
| v1 | 行为克隆「随机最短路第一步」 | **0.000** | 标签本身歧义：BFS 的固定 tie-break 让 97% 的帧都是 right/down，模型学到方向先验 |
| v2 | 换成全局平均池化 CNN | **0.000** | 池化抹掉位置，模型不知道 agent 在哪 |
| v3 | 值函数（MSE 回归 4 个动作的距离） | **0.000** | 见下 |
| v4 | 值函数 + CE（把值转成 softmax 目标分布） | 0.090 | 标签对了，但只训了 300 个迷宫 / 12 epoch |
| **v5** | **同 v4，规模 ×5，epoch ×3.3** | **0.710** | — |

### 3.3 三个必须记下来的诊断

**(a) 感知不是瓶颈 —— 用探针证明，不是靠猜。**
`probe_localise.py` 在冻结 trunk 上接两个线性头，预测 agent 格和 goal 格（64 类）：

| trunk | agent-cell acc | goal-cell acc |
|---|---|---|
| 空间 CNN（保留布局） | **0.998** | **0.996** |
| 全局池化 CNN（对照） | 0.016 | 0.024（= 随机） |

探针本身的两次翻车也记录在案，因为它正是仓库一贯警惕的那类错误：
* 第一次用**一个** 64 类头同时预测 agent 和 goal，argmax 只能输出一个类，
  两个准确率互补（0.902 / 0.098），看起来像「模型只会找 agent」——实际是探针的构造错误。
* 修成两个头之后，发现起点终点是**固定**的，位置标签是常数，探针只需学常量就到 1.000。
  随机化起终点后才有意义。

**(b) MSE 是错的损失，理由是尺度。**
值函数版用 MSE 回归「走完这步后到 goal 的 BFS 距离」，墙惩罚 -32，真实距离 -1..-12。
平方误差被惩罚项主导，绝大部分容量花在「这个方向是不是墙」（局部、好学的题），
而不是「goal 在哪个方向」（真正决定成败的题）。换成 CE（把奖励向量 softmax 成目标分布）
后，同步训练 12 epoch 的一致率从 0.39 升到 0.61，且仍在上升。

**(c) 错误分类告诉你下一步该做什么。**
`analyse_errors.py` 对 4102 个决策步分类：

| 错误类型 | 占比 |
|---|---|
| E1 撞墙（选到被墙挡住的方向） | **0.0000** |
| E2 选了合法但非最优的方向 | 0.5861 |
| E3 振荡（两步来回） | 0.1792 |
| 正确 | 0.2348 |

**模型从不撞墙。** 失败全部是「知道哪条路合法，但不知道选哪条」。
严格降低真实 BFS 距离的步数占比只有 0.3432 —— 而不可逆迷宫里 ~12 步的路径
需要这个比例接近 0.95 才能保证到达。

### 3.4 为什么「单帧 61% 准确」等于「闭环 9%」

这是本文最重要的一条定量结论，也是整个方向的**设计约束**：

> 迷宫是**不可逆**的：走错一步可能进死路，贪心策略再也回不来。
> 若每步正确概率为 p，走完 k 步的概率约 p^k。p=0.61、k≈12 时，
> 闭环成功率必然接近 0（0.61^12 ≈ 0.003）。**所以每步 61% 和闭环 9% 不是矛盾，是同一个事实的两面。**

这条对真实浏览器同样成立：点错一个面板可能就丢状态了。

**两个候选修法，都测了：**

| 修法 | 做法 | 结果 |
|---|---|---|
| (A) 帧堆叠 K=4 | 把最近 4 帧拼起来当输入 | **更差**（一致率 0.26） |
| (B) 多步 lookahead | 每 tick 跑 N 次前向模拟未来，取最好的第一步 | **更差**（成功率 0.020） |

(A) 更差的**原因值得写清楚**：监督标签只依赖当前帧，历史帧是纯噪声输入，
还挤占了容量。记忆要配着「历史相关的标签」才有意义。
(B) 更差的原因：lookahead 用策略自己的输出给叶节点打分，而策略的输出本身
就是错的（61%），用错误信念做规划没有收益。

**真正奏效的是把每步准确率推上去**：把规模从 300 迷宫 / 12 epoch 提到
1500 迷宫 / 40 epoch、宽度 32→48、深度 3→4，一致率 0.61 → **0.86**，
闭环成功率 0.09 → **0.71**。

### 3.5 决定性实验：感知 + 符号规划器 vs 学到的策略

前面所有的实验都在学一个**策略网络**。但错误分类已经指出失败模式是
「知道哪条路合法，但不知道选哪条」—— 这是**规划**问题，不是感知问题。
于是直接测另一个架构：把规划交给确定性求解器，模型只做感知。

```
像素 ─> 三个小检测器（agent 格 / goal 格 / 墙图）
     ─> 确定性 BFS 在解码出的地图上规划
     ─> 每 tick 输出一个动作
```

**没有任何学习到的策略**，检测器 17.0M 参数。

| 架构 | 闭环成功率 | 平均 tick | 参数量 | 决策延迟 |
|---|---|---|---|---|
| oracle 地图 + BFS（上界） | 1.000 | 5.92 | 0 | — |
| **最终检测器 + BFS** | **1.000**（3/3 seed） | **5.9** | 17.0M | 9.85 ms |
| 纯像素策略网络（CE 值函数） | 0.710 | 10.8 | 7.2M | 2.09 ms |
| 随机 / 手写启发式 | 0.000 | — | — | — |

最终检测器（`final_detector.py`，三个修复全部应用）的逐 seed 结果：

| seed | agent acc | goal acc | wall acc | 闭环成功率 | 平均 tick |
|---|---|---|---|---|---|
| 0 | 1.0000 | 1.0000 | 1.0000 | **1.000** | 5.9 |
| 1 | 1.0000 | 1.0000 | 1.0000 | **1.000** | 5.9 |
| 2 | 1.0000 | 1.0000 | 1.0000 | **1.000** | 5.9 |
| **均值 / 最差 seed** | **1.0000 / 1.0000** | 1.0000 / 1.0000 | 1.0000 / 1.0000 | **1.000 / 1.000** | 5.9 |

**结论：正确的架构是「小感知模型 + 符号规划器」，不是更大的策略网络。**
纯像素策略网络即使有 7.2M 参数、每步和 oracle 的一致率 0.86，仍然比
「感知 + BFS」差 29 个点，因为它必须把规划内化到权重里，而内化的规划
是错的。感知部分几乎完美（1.000 / 1.000），规划交给 BFS 后成功率 1.000，
平均 tick 数与 oracle 完全一致（5.9）—— 即**感知误差为 0，规划误差也为 0**。

**这条结论对本方向的架构选择是决定性的：**
小模型应该做**感知和候选打分**（这正是 GUI 侧已经验证的），
**规划应该交给确定性求解器**（BFS、A*、状态机、规则），
而不是指望小模型把规划学出来。

**但要注意延迟代价**：检测器 9.85 ms/次 ≈ 101 decisions/s，比纯策略网络
（2.09 ms ≈ 478/s）慢 4.7 倍。101 Hz 对 15–60 Hz 的游戏控制环**仍然够用**，
但如果目标游戏需要 120 Hz 以上，就该用「检测器降频 + 规划器高频」的混合架构
（`hybrid_arch.py`）。

### 3.6 检测器的 bimodal 塌缩：一次成功不能当结论

**这一节记录了本文最重要的一次自我修正。**

`perception_solver.py` 第一次跑出 agent 0.9963 / goal 0.9963 / wall 1.0000、
闭环 0.990 —— 看起来「感知 + BFS」完胜策略网络。但**同样的代码重跑就塌缩**。

用 3 个固定种子、同一损失函数做对照：

| 配置 | seed 0 | seed 1 | seed 2 | 均值 | **最差 seed** |
|---|---|---|---|---|---|
| C1 只做位置 CE（**无墙任务**） | 0.0150 | **1.0000** | 0.0075 | 0.3408 | **0.0075** |
| C2 位置 CE + 墙 BCE(pos_weight=3) | 0.0150 | **1.0000** | 0.0075 | 0.3408 | **0.0075** |

两个关键事实：

1. **墙任务不是原因。** C1 完全没有墙任务，同样 bimodal。
2. **墙任务本身非常容易。** 所有 seed 的 wall-cell 准确率都是 1.0000，
   包括「塌缩」的那两个 seed。

所以失败的性质是：**「定位一个稀疏的、需要在空间上分辨的目标」这个优化问题
是双峰的** —— 从随机初始化出发，优化要么跳到正确解，要么掉进「输出常数」的
退化解，而且掉进去就出不来。机制在 §3.7 被钉死。

**方法论结论（比这个具体实验更重要）**：
> **报告均值 + 最差 seed，而不是只报一次成功的数字。**
> 一次跑出 0.996 不构成证据；3 个 seed 里 1 个成功、2 个失败，
> 意味着真实期望约 0.34 而不是 0.99。

这条与仓库既有教训同源：`README` 里「planning closed loop 0.475 vs beam 0.000」
和 `docs/planning-report.md` §4.6「train acc 等于全负基线 = head 根本没学任何东西」
—— 都是靠**对照和基线**而不是单次数字识别的。

### 3.7 归因：塌缩解是「不看图像」的捷径

两个独立的实验用两种不同的方式触发了同一个塌缩，把机制钉死了。

**实验一：改变 trunk 的输入通路**（`trunk_attribution.py`，3 seeds，位置 CE only）

| 变体 | 结构 | agent 均值 | **agent 最差 seed** |
|---|---|---|---|
| A | 坐标通道 + 256 投影 | 1.0000 | **1.0000** |
| B | 无坐标通道、无投影 | 1.0000 | **1.0000** |
| C | 无坐标通道 + 256 投影 | 1.0000 | **1.0000** |
| **D** | **坐标通道、无投影** | 0.3482 | **0.0213** ← 塌缩 |

**实验二：改变 head 的初始 logit 尺度**（`head_init.py`，3 seeds，trunk 初始化固定）

| head 权重缩放 | agent 均值 | **agent 最差 seed** |
|---|---|---|
| 0.1 | 0.9914 | 0.9742 |
| 1.0 | 1.0000 | **1.0000** |
| **10.0** | 0.0211 | **0.0192** ← 塌缩 |

**统一机制：塌缩解是「不看图像」的退化解。**

* 变体 D 给模型提供了一条**与像素无关的位置捷径**（归一化坐标通道），
  而没有投影层去稀释它 —— 模型发现「读坐标就能答」，于是从不学图像。
  坐标通道本身不是问题（A 也有），**问题是它能绕过视觉**。
* head 缩放 10 让初始 logit 尺度过大，CE 的早期梯度把 trunk 推成常数输出 ——
  同样是「不看图」的解。

两种塌缩都不是「学不动」，而是**「学到了错误的捷径」**。
塌缩解和正确解在训练损失上没有本质区别（常数解的 loss 甚至更低），
所以必须靠多 seed 才能发现。

**这条对整个方向的架构含义**：
> **任何能让模型绕过视觉的输入通路（坐标通道、位置编码、绝对位置特征），
> 都会诱发捷径解。** UI 侧的 actor 之所以稳定，正是因为它的候选输入
> 只有**裁剪图 + 归一化位置框**，而位置框是相对候选自身的、不指向答案 ——
> 唯一的全局信息（整屏）又必须经过投影。

**可操作的修复**（两种都验证过）：
1. **head 初始 logit 尺度**：`scale=1.0` 稳定，`scale=10` 塌缩。默认的
   PyTorch 初始化（Linear 默认 kaiming uniform）落在安全区。
2. **给坐标类捷径加投影**：任何位置类输入在进入主干前先过一层非线性投影。

### 3.8 修法尝试：空间 softmax 定位（**结果为负**）

「让全局分类头从池化特征里恢复位置」既然是脆的，就试一个更标准的替代方案：
**空间 softmax（soft-argmax over a feature map）** —— 把定位变成平移等变的。

```
特征图 f (B,C,16,16) ─> 1x1 conv ─> 位置 logits (B,16,16)
                                    │
                         softmax over 256 个位置
                                    │
                     (x,y) = Σ_ij p_ij · (x_ij, y_ij)
```

三个理论优势：平移等变、密集监督（高斯热图）、梯度条件好。
对照实验（`spatial_softmax.py`，3 seeds，位置 CE vs 高斯热图 MSE）：

| 方案 | agent 均值 | **agent 最差 seed** | goal 均值 |
|---|---|---|---|
| **A 全局分类（64 类 CE）** | **1.0000** | **1.0000** | 1.0000 |
| B 空间 softmax（热图 + soft-argmax） | 0.0607 | 0.0607 | 0.0467 |
| C 空间 softmax + 墙头 | 0.0607 | 0.0607 | 0.0467 |

**负结果，而且原因清楚**：目标是**离散的单一格子**，不是连续坐标。
16×16 的输出网格对应 8×8 的逻辑网格，每个真实格子覆盖 2×2 输出像素。
热图的概率质量被约束在这个 2×2 块内，soft-argmax 的期望落在块的中间 ——
也就是**格边界上**，读出时系统性偏半格。

**结论：在「离散格子定位」这个任务上，全局分类不仅更简单，而且严格更好。**
空间 softmax 适合的是连续坐标回归（手部关键点、人脸框中心），
那里亚格精度才值钱。**任务形式决定了 head 的形式**，不能因为某个 head 更"现代"就用它。

（这个实验还踩了两次自己的 bug，都记在代码注释里：先是直接对 16×16 输出图做
argmax 却当成 8×8 格索引（得 0.0000），修成 soft-argmax 读出后是 0.0607。
**0.0000 和 0.0607 之间隔着一个坐标约定，不是两个方案的性能差。**）

### 3.9 修复方案与最终架构

综合以上，检测器最终架构：

```
输入 (128×128 像素)
  │
  ├─ conv stack（无坐标通道）──> 特征图 (C×16×16)
  │                              │
  │                    flatten ─> Linear(→256)  ← 投影层：阻断捷径
  │                              │
  │                    ┌─────────┴─────────┐
  │              agent head          goal head      （64 类 CE）
  │                                             
  └─ 另一路 conv stack ─> wall head（64 格 BCE）
                                    │
                        确定性 BFS 在解码出的地图上规划
```

三个设计要点，每一条都对应上面测到的一个失败：

| 要点 | 防的是什么 |
|---|---|
| **不加坐标通道** | D 变体的捷径解 |
| **特征图 flatten 后必须过 Linear 投影** | D 变体（无投影时坐标/像素都能直达 head） |
| **head 用默认初始化（scale≈1）** | head_scale=10 的塌缩 |
| **位置与墙分两个 trunk** | 仓库 README 的 single-tower 多任务冲突（0.650 vs 0.887） |
| **规划交给 BFS** | 学出来的策略网络（0.710 vs 0.990） |

### 3.10 混合架构：感知降频 + 规划高频

最终检测器 13.61 ms/次（73 Hz）。对 15–60 Hz 的游戏够用，但如果目标要 120 Hz 以上，
就需要把感知和规划解耦：**检测器每隔 N tick 跑一次并刷新地图，规划器每 tick
在缓存的地图上重算**（BFS 只花微秒级）。

用最终检测器实测这条曲线（`hybrid_final.py`）：

| 检测器每 N tick 跑一次 | 闭环成功率 | 平均 tick | 每个迷宫检测次数 | 摊薄 ms/tick | 有效频率 |
|---|---|---|---|---|---|
| 1 | 1.000 | 5.9 | 5.9 | 13.61 | 73 Hz |
| 2 | 1.000 | 5.9 | 3.2 | 6.81 | 147 Hz |
| 4 | 1.000 | 5.9 | 1.9 | 3.40 | 294 Hz |
| 8 | 1.000 | 5.9 | 1.2 | 1.70 | 588 Hz |
| **16** | **1.000** | **5.9** | **1.0** | **0.85** | **1175 Hz** |

**降频到 1/16，成功率一点不掉**（还是 1.000，平均 tick 还是 5.9）。
原因很直接：迷宫是**静态**的 —— 墙不变，goal 不变，只有 agent 在动，
而 agent 的位置规划器本来就知道。所以感知的结果在一次迷宫里只需要刷新一次。

**这条曲线的真正含义不是"迷宫简单"，而是一个可迁移的架构模式**：
> **慢感知 + 快规划 + 状态缓存。**
> 把不随时间变化的东西（界面结构、地图、DOM 布局）交给慢模型，
> 把随时间变化的东西交给快求解器。真实浏览器同理：
> 页面结构在多次点击之间通常不变，需要重新感知的频率远低于点击频率。

### 3.11 策略网络的分布外泛化：能力悬崖在网格尺寸上

策略网络（不是感知+规划）在**训练分布之外**的五个域上评测
（`eval_generalisation.py`，200 个迷宫/域，预算 24 tick）：

| 域 | 与训练分布的差异 | 成功率 | 平均 tick |
|---|---|---|---|
| D0 | 无（训练分布） | 0.890 | 7.6 |
| D1 | 墙更密（p 0.22 → 0.32） | 0.850 | 8.3 |
| D2 | 墙更疏（p 0.22 → 0.12） | 0.965 | 6.3 |
| **D3** | **网格 8×8 → 12×12**（每格 16px → 10px） | **0.010** | 47.5 |
| D4 | 墙变成 2×2 厚块 | 0.890 | 7.7 |
| **D5** | **整体换配色** | **0.875** | 8.1 |

两条结论：

* **D5 是正面证据**：换掉全部颜色后仍有 0.875，说明模型学的是**几何关系**
  （谁在上方、谁需要绕路），不是记住了「蓝色圆=agent」这类表面特征。
  这与 §3.7 的机制一致 —— 模型确实在看图。
* **D3 是能力悬崖**：网格尺寸从 8×8 变 12×12，成功率从 0.890 崩到 0.010。
  每格的像素从 16 降到 10（缩小 37%），策略就完全失效。

**D3 说明什么**：策略网络的容量不是被「样本数」限制，而是被**输入分辨率下的
空间结构可辨度**限制。8×8@128px 下每格 16px，CNN 能把「哪一格」编码清楚；
12×12 下每格 10px，加上路径长度翻倍，最优路径的搜索空间和所需精度都变了。

> 这直接给出工程结论：**换一个更难的关卡/更大的画布之前，先确认输入分辨率
> 还够不够让空间结构可辨。** 公开的 GUI 工作里「zoom-in / 提高分辨率」是
> 最大的单项杠杆（+5~9 点），与这里的 D3 是同一件事。

（注意：`eval_generalisation.py` 的第一版有个自写的 bug —— 每 tick 都喂**初始帧**，
模型看不到 agent 移动，导致所有域都被压到 0.175。修正为每 tick 重新渲染后
才是上面的数字。这个 bug 与 §2.3 的视口 bug 是同一类：**评测代码的错误会伪装成
模型的能力边界。**）

### 3.12 检测器训练的一个坑：共享 trunk 的多任务冲突

第一版检测器用**一个共享 trunk** + 联合损失（agent/goal 用 CE，墙用 BCE），
结果：

| epoch | agent acc | goal acc | wall-cell acc |
|---|---|---|---|
| 5 | 0.024（随机） | 0.014（随机） | 0.8744 |
| 10 | 0.629 | 0.825 | 1.0000 |

密集的墙 BCE 项**淹没了稀疏的 agent/goal CE 信号** —— 共享 trunk 只学会了
输出墙图的多数类常数。改成**两个独立 trunk**（位置一个、墙一个）后，
15 epoch 就到 agent 0.996 / goal 0.996 / wall 1.000。

这和仓库 README 里那条结论**同构**：「single tower, mixed tasks → 0.650，
dual tower + question gate → 0.887」。多任务冲突在视觉塔上重演了一次，
解法也一样：**拆塔**。

| 指标 | 值 |
|---|---|
| 闭环成功率（200 held-out 迷宫，预算 24 tick） | **0.710**（oracle 1.000） |

## 4. 四个方法论教训（与仓库主线一致）

1. **表征要先探针，再训练。** 仓库的第一条经验（README「The one result that
   transfers」）：三分钟的线性探针能提前回答任务成败。本文的迷宫链路上，
   探针立刻发现感知不是瓶颈，从而避免了在加大模型上浪费时间 —— 而加大模型
   **确实**有效（0.61→0.86），所以这个"省下的时间"最终没有浪费，但顺序是对的。

2. **「消融到 1.000」是基准坏了，不是模型好了。** v1 基准的所有变体都是 1.000，
   这在仓库里也有先例：`vision-competence.md` 的 CNN 变体也是满分的空间/场景任务，
   后来换编码器才看出差别。基准必须先有一个**强启发式打不过**的对照。

3. **一次前向的决策头，比自回归解码更适合实时。** 这与 §1 的延迟实测一致，
   也和公开的三种做法（GUI-Actor 注意力动作头、PlayJev 的选项概率读出、
   NorthCUA 的有限动作直接选择）指向同一个方向。

4. **报「均值 + 最差 seed」，不报单次数字。** 这是本轮最贵的一课。
   感知检测器第一次跑出 0.9963 / 闭环 0.990，换个种子就塌缩到 0.0150；
   而真浏览器 grounding 也从 0.200（三处评测 bug）修到 1.000。
   **两个方向的错误都来自「只跑一次就下结论」。**

   同类错误的另一个版本：评测代码本身的 bug 会伪装成模型的能力边界。
   本轮踩到两次 —— 真浏览器视口设成模型输入尺寸（0.200），
   泛化评测每 tick 喂初始帧（0.175）。**每一次都要用「正确实现 vs 明显错误实现」
   的对照来验证评测器本身。**

5. **更"现代"的 head 不一定更好，要看任务形式。** 空间 softmax 是定位的标准做法，
   在这个任务上却是 0.0607 vs 全局分类的 1.0000 —— 因为目标是**离散格子**，
   亚格精度没有价值，反而引入了读出偏差。**任务形式决定 head 的形式。**
