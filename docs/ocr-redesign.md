# OCR 重设计：借鉴 DeepSeek-OCR（v1）

> 日期：2026-11-09
> 触发原因：基础识图 0.95 通过后，OCR 三族全部失败（doc_field 0.01、
> char_read 0.03、text_locate 0.23 ≈ 随机）
> 参考：DeepSeek-OCR（arXiv 2510.18234）、DeepSeek-OCR 2 / DeepEncoder V2
> （2601.20552，见 deepseek-technique-audit.md §3）

## 0. 原版 DeepSeek-OCR 的核心设计（已核摘要）

**架构**：DeepEncoder + DeepSeek3B-MoE-A570M 解码器。

关键设计点：

1. **DeepEncoder：高分辨率输入、低激活、高压缩**
   - SAM（窗口注意力，高分辨率下激活可控）
     + 16x 卷积压缩 token 数
     + CLIP（全局注意力，在压缩后的少量 token 上做）
   - 两个视觉部件是**串联**的：先用便宜的局部注意力消化大图，
     再用贵的全局注意力处理压缩后的 token。

2. **光学压缩作为"上下文压缩"**
   - 文本 token : 视觉 token < 10x 时，OCR 精度 97%
   - 20x 时仍有 60%
   - 也就是说：**一页文本可以被压进几十个视觉 token 里再解出来**

3. **解码器是 MoE**（3B 总参 / 570M 激活）——和 Jaume 同款架构取向。

4. **训练数据由模型自己产**：单卡 A100 一天 20 万页，
   数据飞轮不依赖人工标注。

## 1. 我们 OCR 失败的根因分析

| 症状 | 根因 |
|---|---|
| doc_field ≈ 0 | 答案是 6 位发票号，4800 个不同答案在 151647 词表里做**整串分类**，
  每个答案只有 1-2 个样本 —— **任务结构错误** |
| char_read ≈ 0.03 | 同上，且 4 字符码组合空间巨大 |
| text_locate 0.23 | 224px 下 box 内文字约 13px，接近可读下限；
  且 SigLIP2 的 196 token 里，一个 130px 的 box 只占 ~7x7=49 token |
| 训练崩（320px） | 位置编码插值后 NPU 向量核异常 —— 算子兼容性 |

三条结构性错误：**答案表示错**（整串分类而非逐字符）、
**分辨率/token 预算错**（小字被压缩到不可读）、
**没有压缩比意识**（直接把原图 token 塞给骨干）。

## 2. 借鉴 DeepSeek-OCR 的改造方案

### 2.1 逐字符生成头（最重要，成本最低）

DeepSeek-OCR 的解码器是**自回归生成文本**，不是从词表里选整串答案。
改成：

- 答案按字符级 target：数字 0-9、大写字母 26、特殊符（$、box1-4），
  词表 ≤ 50
- 用一个小字符头（d → 50），对答案 span 做逐位 CE
- 模型规模不变，任务从"4800 类分类"变成"最多 8 步的 50 类序列生成"

这一条不借鉴任何外部设计也该做——是我们在 OCR 任务结构上的 bug。

### 2.2 两段式视觉塔（SAM→conv→CLIP 的思路）

我们现在的 SigLIP2 是 16x16 patch 全局注意力，1024px 文档要 4096 token，
不可行。改造：

- **局部段**：小 kernel 卷积 / 窗口注意力在原生高分辨率上提取字形特征
  （激活可控，类似 SAM 的窗口设计）
- **压缩段**：conv stride 或 pooling 把 token 数压到 64-256
- **全局段**：SigLIP2 在压缩后的 token 上做全局注意力

对 61GB 单卡，这个结构让"高分辨率 OCR"和"冻结视觉塔"可以同时成立。

### 2.3 压缩比作为显式设计参数

DeepSeek-OCR 把"文本 token / 视觉 token"当作一等指标。我们之后报 OCR
结果时也带这个数：一页 300 字 ≈ 400 文本 token，用 64/128/256 视觉 token
分别是 6x/3x/1.5x 压缩。**先报压缩比，再报精度**，才能和文献对齐。

### 2.4 数据飞轮（后期）

合成渲染器已经验证过（发票/字符/网格都是本地 Pillow 出的），
天然可以批量产带标注的文档图。DeepSeek-OCR 的"200k 页/天"在这个规模上
等价于"渲染器想跑多快跑多快"。前期不需要，等字符级头跑通后再上量。

### 2.5 DeepSeek-OCR 2 的语义重排（远期）

DeepEncoder V2 按**语义**重排视觉 token（而非光栅顺序），用两个级联 1D
因果结构实现。审计文档的建议仍然成立：有意思但改动大，放在 UI 模型阶段
再评估——UI 密集布局恰好是"光栅顺序不友好"的场景，届时价值更高。

## 3. 立即可做的最小验证（按性价比排序）

1. **字符级头重跑 char_read**：只改答案表示，其他不动。
   判据：4 字符码 exact match > 0.5 即说明"整串分类"确实是根因。
2. **text_locate 提分辨率**：224 → 448（原生位置编码插值在 448 会再崩，
   改用双线性放大小图到 448 而不动位置编码——等效于"更清晰的 196 token"）。
   判据：> 0.6 说明分辨率是主因。
3. 两项都过 → 再谈两段式视觉塔；都不过 → 问题在桥接容量，回 SigLIP2 换
   so400m 大杯。

## 4. 与 Jev 的关系

OCR 失败暴露的三个问题（答案表示、token 预算、压缩比）全部是**接口层**
的，不动 Jaume 骨干。Jev 系列的视觉规格直接按 DeepSeek-OCR 的结构写：

- 视觉塔：局部高分辨率段 + 压缩 + 全局段（两段式）
- 显式记录压缩比
- 解码：逐字符/逐 token 生成，禁止整串分类
