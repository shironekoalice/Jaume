## 0. 一句话结论

**TTC（层路径推理）方向以负结果结题：oracle 增益真实存在（0.7113 vs 0.3503），但所有 input-blind 机制都取不出来。**
因此转向规划，且**不再假设"换个任务就能变好"** —— 新方向的第一步不是训练，而是**先证明小模型在可验证规划任务上存在可提取的搜索增益**。

## 1. 为什么转向规划（承接 TTC 的负结果）

### 1.1 TTC 三轮闸门的最终账

| 实验 | 关键数字 | 判定 |
|---|---|---|
| T0 冻结 backbone 三分类 | 0.3502 [0.3349, 0.3589] vs 地板 0.1961 | **PASS** |
| Gate 0 归因（v4，3 seeds） | A=0.3503 / B=0.3448 / C=0.3553 / D(oracle)=0.7113，coverage 0.751 | **FAIL** |
| Gate 1 前缀选择器 | G1=0.3324，**G1-rand=0.3483 反超** | **FAIL** |
| Gate 1b 置信度自适应 | budget16: adapt 0.3470 vs **shuffle 0.3826** | **FAIL** |

**三条不可回避的教训**：

1. **oracle 有增益 ≠ 增益可学习。** D−A=+0.361，但 C−A=+0.0049 落在 seed sd（0.0140）内。
2. **集成在判别任务上不是"变强"，而是"变钝"。** 路径多样性扩充到 174 条后结论不变，排除了"相关性太高"这一解释。
3. **置信度不是可用的路由信号。** 打乱置信度反而更好，说明模型给自己的打分与"这条路径是否答对"无关。

### 1.2 由此得到的选型约束（写死，不再回头）

- **不再做 input-blind 的组合类方法**（集成/固定路径/静态剪枝作为主贡献）。
- **任何"条件化"主张必须有 input-blind 对照**，且对照要能在同一预算下胜出（文献 2610.10368 的硬性要求）。
- **优先选择能算精确最优的任务**，否则"没提升"无法区分是方法差还是任务太难。

## 2. 任务选择：为什么不是 ALFWorld

ALFWorld 是文本具身规划的标准 benchmark，但**与 Jaume 的头结构不匹配**：

| 维度 | ALFWorld | Jaume 现有能力 |
|---|---|---|
| 动作空间 | 自由文本（`go to fridge 1`） | 候选打分（Choice/Score/Noul） |
| 需要的能力 | **生成**合法指令 + 长程记忆 | **判别**哪个候选更好 |
| 350M 的表现 | 需要大模型 + 重 prompt 工程 | 编码器打分头天然适配 |

**实测**：`textworld` 的 C++ 扩展在本机编译 20+ 分钟仍停在 0–1% CPU，已放弃安装。

### 2.1 采用：约束满足规划（`PlanningEnv`）

```
items = {0..n-1}          slots = {0..m-1}
state = assignment[item] -> slot | -1（未放置）
action = place(item, slot) | remove(item)
goal  = before(a,b) / not_same(a,b) / same(a,b) / fixed(a,s)
```

三个关键性质：

1. **精确最优可暴力枚举**（默认 6×4 网格，m^n ≤ 10^6），所以能报**与最优的差距**，而不只是成败。
2. **难度是单一旋钮**（约束数），"模型从哪一档开始有用"变成可测量的问题。
3. **奖励稠密可验证**：状态要么满足全部约束，要么不满足。

代价（诚实记录）：这是**自造任务**，不是公认 benchmark，审稿人会质疑外部效度。缓解方案见 §5。

## 3. 基线：手写启发式已经很强（这是核心难点）

在 300 训练任务、100 测试任务、budget=30 的设置下（已跑完，日志 `/mnt/workspace/plan-train.log`）：

| 条件 | success | progress |
|---|---|---|
| random | 0.017 | 0.312 |
| **greedy（手写约束进度）** | **0.827** | 0.972 |
| optimal（暴力最优） | 1.000 | 1.000 |

另一组更小的扫描（30 任务 / budget 40，`plan_search.py`）：

| 约束数 | random | greedy |
|---|---|---|
| 4 | 16.7% | 50.0% |
| 8 | 0.0% | **83.3%** |
| 12 | 0.0% | 66.7% |

**判读**：greedy 在 8 约束档就达到 83%，说明**这个任务上"能算的东西没必要学"**。
因此本方向若要有价值，模型必须回答的不是"能不能规划"，而是：

> **在 greedy 已经很强的档位上，学习到的打分能不能在同等搜索预算下超过它？**

这是一个**更窄、也更可信**的科学问题 —— 且与 TTC 的失败模式同构（oracle 有空间，但取不出来），所以结论无论正负都有信息量。

## 4. P0 闸门：ScoreHead 引导搜索（进行中）

### 4.1 协议（已实现，`plan_train.py`）

1. 冻结 Jaume-Causal 350M backbone，只训打分头 `ScoreModel(d, d)`（state 与 action 各自编码后交互）。
2. 训练标签：greedy rollout（正）+ 2 条随机 rollout（按"是否落在某条最优完整解上"打 0/1）+ 1 条最优 rollout（正）。
3. 规模：300 训练任务 → **22,836 个 (state, action) 对**，正例率 0.382，嵌入耗时 148s，30 epoch。
4. 评估：100 个 held-out 任务，**beam width 3、budget 30**，与 greedy / random 同预算对比。
5. 判据：`beam-model − greedy > 2×binomial_noise` 才算 PASS。

### 4.2 已完成部分

```
greedy   success=0.827  progress=0.972
random   success=0.017  progress=0.312
optimal  success=1.000  progress=1.000
head train-label accuracy: 0.757    (22836 pairs, 148s embedding)
```

**注意**：0.757 是**训练集标签拟合度**，不是泛化指标，不能作为"方法有效"的证据。

### 4.3 第一个 bug：训练 / 评估输入分布不一致（2026-11-04 发现）

| 位置 | action 的编码方式 |
|---|---|
| 训练 `collect()` | `action_text(a)` —— **单独**编码 |
| 评估 `beam_search()`（旧版） | `ctx + " " + action_text(a)` —— 带上了 state 前缀 |

打分头训练时**从未见过**带 state 前缀的 action 文本，评估时却全部喂这种输入。
旧版评估结果即使跑完也不可信 —— 它测的不是训练好的那个函数。

同时修掉了性能问题：旧版对每个候选动作都重编码一次 state，
合计约 **22.5 万次 encoder 调用**。现在同一 step 内所有 beam 的 state 合并成一次
batch 前向，action embedding 按文本缓存（动作只有 30 种），
调用次数降到 **约 3 千次（降 ~74 倍）**。

修复后本机 Intel 核显实测 **13.7 s/任务**（100 任务约 23 分钟）。

### 4.4 第二个 bug：embedding 尺度不一致 —— 这才是 −0.81 的真凶（2026-11-07）

修完上面的 bug 重跑，结果仍然是 `beam-model = 0.000`（对比 greedy 0.810）。
换到远端 910B3 用**修复前**的旧代码跑，结果**一模一样**：

```
远端 11-04（旧代码）：  beam-model 0.000   gain = −0.8100
本机 11-07（新代码）：  beam-model 0.000   gain = −0.8100
```

两个独立实现给出**同一个错误数字** —— 这恰恰说明人眼审查看不住这类 bug。
查下去发现第二个不一致：

| | 输入给打分头的东西 | 向量范数 |
|---|---|---|
| **训练** | `embed(...)` 原始 mean-pooled 向量 | **~12.2**（state）/ ~14.6（action） |
| **评估** | `F.normalize(embed(...))` | **1.0** |

打分头第一层是 `Linear(1024, 256)`，输入尺度被缩小了十几倍，
输出直接饱和 → **所有动作拿到几乎相同的分数** → beam 排序退化 → 等价于随机游走。

**修复**：新增唯一入口 `embed_pair()`（强制 L2 归一化），
训练侧与评分侧都走它，从结构上杜绝两边再次漂移。
并加了 `tests/test_scoring_consistency.py`（4 项）用 AST 静态检查
"评分脚本里不允许出现裸 `embed()` 调用" —— 这类 bug 本该被测试拦住。

### 4.5 机制诊断：beam search 没问题，问题 100% 在 head（2026-11-07）

在改标签之前，先把"机制坏了"和"head 没学到"分开。
做法是**用三档不同的分数驱动同一个 beam search**：

| beam 驱动的分数 | success | progress | 说明 |
|---|---|---|---|
| **oracle**（暴力枚举最优动作集） | **1.000** | 1.000 | 机制的上限 |
| **greedy-score**（手写即时约束进度） | **0.900** | 0.900 | 机制的可行性 |
| **head**（训练出来的打分头） | **0.000** | 0.000 | 方法本身 |

**三条结论**：

1. **beam search 实现是好的** —— 换成完美分数能到 1.000。
2. **"打分引导搜索"这个范式是有效的** —— 用手写分数做引导，
   beam search 达到 **0.900，反而高于 greedy 本身的 0.810**
   （beam 保留了多条路径，比单条 myopic 贪心更稳）。
   这是一个**正面结果**，而且是产品化的抓手。
3. **原方法 0.000 的原因完全在 head**，与搜索机制无关。

进一步的 head 诊断（同样在 910B3 上）：

| 指标 | head | greedy |
|---|---|---|
| top-1 动作落在最优动作集里的比例 | **0.350** | **1.000** |
| 同一状态下各动作分数的标准差 | 0.134 | — |

首步 trace 更能说明问题：head 的 top-3 几乎总是
`place item2 at slot3` / `place item3 at slot3` —— **它在学一个动作先验（"选 slot3"），
几乎没有在用状态**。

### 4.6 BCE 下的三标签对照 —— 三个 head 全部塌缩（910B3，2026-11-07）

一次嵌入、三套标签、同一套 head 结构、同一批测试任务（`scripts/plan_head_study.py`）：

| 标签 | 正例率 | train acc | **全负基线** | beam success | beam progress |
|---|---|---|---|---|---|
| optimal-next | 0.018 | 0.982 | **0.982** | **0.000** | 0.438 |
| imitation | 0.025 | 0.975 | **0.975** | **0.020** | 0.445 |
| in-optimal | 0.138 | 0.872 | 0.862 | （见 JSON） | — |

**train acc 等于全负基线 = head 根本没有学任何东西。**
训练 loss 也几乎不动（optimal-next: 0.0456 → 0.0430，起点约 −log(0.018) ≈ 0.078）。

这暴露了第三个、也是最根本的设计错误。

### 4.7 第三个设计错误：损失函数把"选择"变成了"打分"

原来的损失是**对每个 (state, action) 对独立做二元交叉熵**：

```
loss = BCE(head(concat(s, a)),  y[state, action])
```

在这个形式下，"永远预测负例"就是一个接近最优的解 —— 正例率 1.8% 时，全负的 loss 只有 0.078，
比模型要跨过的门槛低得多。更糟的是，**BCE 允许模型完全不看状态**：
只要学一个关于 *action 本身* 的先验（哪些动作在正例里出现得更频繁）就能降低 loss。
诊断里看到的正是这个退化 —— head 的 top-3 永远是 `place itemX at slot3`。

但我们要学的根本不是"这个动作好不好"，而是**"在这个状态下该选哪个动作"**。
那是一个**状态内部**的排序问题，正确的损失是**状态内 softmax 交叉熵**：

```
loss = CE( head(concat(s, a_1..a_|A|)),  target_action )
```

在这个损失下，**只用动作先验是 provably 无用的** —— 固定先验的 loss 恒为 log|A|，
唯一能降低它的办法就是使用状态信息。

于是设计对照实验（`scripts/plan_ce_study.py`）：

| 维度 | 取值 | 检验什么 |
|---|---|---|
| 损失 | BCE（对） vs **CE（状态内 softmax）** | 是否必须用状态 |
| 标签 | optimal-next / imitation | 哪种监督信号更可学 |
| 编码 | **split**（state 与 action 分开编码） vs **joint**（`state \|\| action` 一起编码） | mean-pooling 是否稀释了对应关系 |

CE 版的 `imitation` 是**能力上限参照**：如果它连 greedy 都学不到，
就说明 350M 基座没把状态暴露给浅层 head —— 那是关于**基座容量**的结论，与标签无关。

### 4.8 CE 版结果：损失函数对了，但表征是瓶颈（910B3 + 本机 XPU）

| 编码 | 标签 | train top-1 | beam success (w=1/3) | beam progress |
|---|---|---|---|---|
| split | imitation | 0.181 | 0.000 / 0.000 | 0.000 |
| split | optimal-next | 0.213 | 0.000 / 0.000 | 0.000 |
| split | in-optimal（BCE） | 0.872（二分类 acc，= 全负基线） | 0.000 | 0.416 |

对照：同一批任务上手写 greedy 的 **top-1 命中率是 1.000**，成功率 0.810。

**怎么读这组数**：

1. **CE 确实比 BCE 好**：CE 的 loss 从 log|A|≈3.18 降到 2.59（= 学到了 1.75 倍于随机的提升），
   而 BCE 的 loss 几乎不动（0.0456→0.0430），三个 head 全部塌缩到全负基线。
2. **但离 greedy 还差得远**：top-1 从 0.042（随机）到 0.21，学到了 5 倍提升，
   但 greedy 是 **1.000**。
3. **score-mode（logit vs log-prob 累加）没有区别** —— 排除了"累加尺度"这个解释。
4. **连"模仿 greedy"都做不到** —— 这是最关键的一条：
   imitation 标签是最容易学的（唯一正例、锐利），如果连它都学不到 greedy 的水平，
   那么问题**不在标签，也不在损失函数**。

**结论：瓶颈在表征。** 冻结的 350M 编码器 + mean pooling + 浅层 head，
拿不到"在给定状态下该选哪个动作"所需的信息。

### 4.9 决定性实验：能力在不在基座里？（`scripts/plan_finetune.py`）—— **部分成立**

结论先写：**假设 (a) 成立 —— 能力在基座里，但 350M 不足以把它完全取出来。**

用 150 个训练任务、imitation 标签（学 greedy 会做什么）、全解冻编码器（291.9M 参数）
端到端训练，**每个 epoch 都报 top-1**：

| epoch | CE loss | top-1（随机基线 1/24 = 0.042） |
|---|---|---|
| 1 | 3.153 | 0.225 |
| 2 | 2.841 | 0.280 |
| 3 | 2.745 | **0.005** ← 瞬时崩塌 |
| 4 | 2.627 | 0.170 |
| 5 | 2.395 | 0.295 |
| 6 | **2.164** | **0.475** |

**与冻结版对照**：

| 训练方式 | epoch 数 | top-1 | CE loss |
|---|---|---|---|
| 冻结 + 浅层 head | 30 | 0.213 | 2.586 |
| **全解冻微调** | **6** | **0.475** | **2.164** |

**微调用 1/5 的 epoch 拿到 2.2 倍的 top-1**。所以"冻结的浅层读出取不出来"这个判断是对的：
能力确实在基座里，只是线性/浅层的读出够不着。

**但绝对水平仍然不够**：0.475 vs greedy 的 **1.000**。
即使允许微调全部 291.9M 参数，模型也只能模仿手写启发式的一半。
**350M 的状态表征不足以支撑"在给定状态下选对动作"** —— 这是一个关于模型容量的结论，
不是关于标签或损失函数的（后者都已被排除，见 §4.7 / §4.8）。

**附带发现：epoch 3 的瞬时崩塌（top-1 = 0.005，比随机还差 8 倍），随后自行恢复。**
loss 全程单调下降，所以这不是发散。这条现象本身值得记录：
在"浅层 head + 全解冻 MoE 编码器"的设置下，优化会经过一个
**损失已降、但排序能力已崩**的区域 —— 即 **CE 损失与 top-1 脱钩**。
诊断脚本已加上三项指标（logit_std / emb_cos / gate_wspread）以便下次定位。

### 4.10 决定性实验：能力在不在基座里？（`scripts/plan_finetune.py`）

冻结表征学不出来，只有两种可能，方向完全相反：

| | 含义 | 如果成立 |
|---|---|---|
| **(a)** 能力**在**基座里，只是冻结的浅层读出取不出来 | 内部能力建设路线**成立** | 微调后 head 应该能追上 greedy |
| **(b)** 能力**不在**基座里 | 这个方向在 350M 上走不通 | 微调后仍然学不会，得换基座/换任务 |

做法：**解冻整个编码器**，用同样的 segment softmax CE 端到端训练
（joint 编码，让编码器直接看到"状态 ‖ 动作"的配对）。
如果微调后 `imitation` 的 top-1 能从 0.21 提到接近 1.0，
那就证明了 (a) —— 这对"用小模型做规划"是一条**明确的正面结论 + 产品路径**。

## 5. 已知风险与对策

| 风险 | 严重度 | 对策 |
|---|---|---|
| 自造任务缺外部效度 | **高** | 至少复现一个公开可验证任务（见 §6）；或在论文中明确定位为"机制诊断"而非"benchmark 刷分" |
| greedy 太强，没有改进空间 | **高** | 提高约束数/网格尺寸做出更难的档位；或改指标为"达到同等成功率所需的搜索步数" |
| beam 评估成本爆炸 | 中 | 缓存 state embedding（同一 state 被多个动作共享，可省 ~1/|A| 次编码）；beam width 降到 2 |
| 350M 打不过手写启发式 | **中高** | 这本身就是可发表结论（"小模型在该类任务上不如启发式"），但要配合更难的档位才成立 |
| 负结果过多，叙事疲惫 | 中 | 把 TTC + Plan 合成一篇"小模型条件化推理的可提取性"报告，负结果成为主线证据 |

## 7. 与整体方向的关系

```
JM（记忆）        → 负结果：记忆不是瓶颈
TTC（层路径推理） → 负结果：oracle 有增益，input-blind 取不出
Plan（本文）      → 在可验证规划上测"打分能否引导搜索"
                    └─ 若正：小模型 + 搜索 的产品化路径
                    └─ 若负：三连负结果 → 一篇"小模型条件化推理边界"的诊断性论文
```

**共同主线**：不是"再训一个更大的模型"，而是**在 350M/16GB 级算力约束下，搞清楚哪些条件化信号真的可学**。
这条主线的好处是：**每个负结果都是可发表的一块**，不会像刷 benchmark 那样一旦没赢就全部作废。

## 8. 复现入口

所有实验都在 `code/repo/scripts/` 下，均支持 `--device npu|cuda|cpu`。

```bash
# 环境自检（不动权重，只验证动作空间与最优解）
python scripts/planning_env.py

# 基线扫描：难度 × 随机/贪心（不需要模型）
python scripts/plan_search.py --n-constraints 4 8 12 --tasks 30 --budget 40

# P0：训练 ScoreHead + beam search 评估
python scripts/plan_train.py \
  --model /mnt/workspace/output/350m-causal-mlm/final \
  --n-constraints 8 --train-tasks 300 --test-tasks 100 --budget 30 \
  --epochs 30 --device npu --out /mnt/workspace/output/plan-train.json
```

**注意（已踩过的坑）**：

- `plan_train.py` 的评估是 `O(test_tasks × budget × width × |A|)` 次模型前向，先按此估算再定规模；
  100 任务 / budget 30 / width 3 实测 > 11 分钟仍未结束（CPU 侧编码瓶颈，非 NPU）。
- 首轮评估建议 `--test-tasks 20 --budget 20` 快速探路，确认方向后再放大。
- 脚本必须 `flush=True` 打印，否则管道下看不到进度。
