# Jaume 基础识图能力画像（Stage 1）

> 日期：2026-11-08
> 代码：vision_suite.py / train_vision_suite.py / vision_baseline.py
> 定位：通用识图（OCR 只是其中一项），UI/GUI/游戏识别是后续独立模型

## 0. 为什么做这个而不是 OCR

产品目标是**通用基础识图能力**。发票 OCR 只是一个子场景，且把精力压在它上面
会让结论局限于一个垂直领域。所以改成测**能力谱系**：属性、计数、空间关系、
比较、场景布局、多属性组合 —— 这些是任何通用视觉模型都要有的地基。

## 1. 任务设计

本地 Pillow 渲染，无下载依赖。六个能力族，全部多选题，答案集固定，
所以各族准确率可直接比较，且多数类基线明确。

| 族 | 问什么 | 选项数 |
|---|---|---|
| attr | 形状 / 颜色 / 大小 | 5 / 6 / 2 |
| count | 某形状有几个 | 5 |
| spatial | 甲在乙的哪一侧 | 4 |
| compare | 哪个颜色更多 | 2 |
| scene | 布局是单/行/网格 | 3 |
| multi_attr | 形状或颜色 | 5 / 6 |

## 2. 结果（9000 训练 / 1200 验证，12 epoch）

| 族 | 准确率 |
|---|---|

| count | 0.240 |
| spatial | 0.275 |
| compare | 0.170 |

| multi_attr | 0.180 |

**全部接近随机。loss 卡在 1.31 不再下降。**

### 2.2 纯 CNN 基线（同样本、同任务，不经过 Jaume）

| 族 | 最好准确率 |
|---|---|

| **scene** | **1.000** |

## 3. 诊断：结论明确

**任务本身是可学的**（CNN 证明 spatial/compare/scene 到 1.0），
**但 Jaume 桥接学不会**（全部 ~0.25）。这不是任务设计问题，是桥接问题。

三个可能原因，按可能性排序：

1. **视觉 token 容量不足。** CNN tower 把 96x96 压缩到 48 个 token，
   再拼上问题 token 送入 16 层。48 个 token 要同时承载形状、颜色、位置，
   信息被稀释。前一阶段形状计数能到 0.99，是因为那个任务只需一个属性。
2. **冻结骨干的语义不匹配。** Jaume 是在纯文本上预训练的，它的注意力
   被训练成"读 token 语义"，而视觉 patch 没有语义先验。冻结前 12 层意味着
   前 12 层必须原样处理视觉 token，这可能是硬约束。
3. **attr 任务本身有捷径冲突**（CNN 也只有 0.36）：小图形带网格背景、
   大图形不带，模型学到"网格=small"后与其他属性冲突。

## 3b. 决定性验证：瓶颈是视觉 token 容量（2026-11-08）

第 3 节的假设 1 被直接验证。同样 9000/1200、10 epoch，只把视觉 token 从
**48 提高到 192**：

| 能力 | token 48 | **token 192** | 变化 |
|---|---|---|---|
| **spatial** | 0.275 | **1.000** | +0.725 |
| **scene** | 0.355 | **1.000** | +0.645 |
| **multi_attr** | 0.180 | **0.795** | +0.615 |
| **attr** | 0.275 | **0.755** | +0.480 |
| compare | 0.170 | 0.450 | +0.280 |
| count | 0.240 | 0.280 | +0.040 |
| **mean** | 0.249 | **0.713** | **+0.464** |

**结论：350M 的 Jaume 文本骨干完全能做通用识图，之前全部失败是视觉 token
容量不足，不是骨干不行。** 三个能力直接打到 1.000，说明空间关系、场景布局
这类需要全局结构的能力，骨干已经具备。

### 3c. 仍然失败的两个能力及其含义

- **count 0.28**：计数需要把分散的同类物体聚合，192 token 仍不够。
  CNN 基线也只有 0.74，说明这个任务对 96x96 输入本来就偏难（物体数量
  与位置耦合）。**属于任务难度，不是桥接缺陷。**
- **compare 0.45**：需要同时比较两个颜色的数量，本质是 count 的复合，
  受同一个限制。

这两个恰好指向一个明确的改进方向：**计数类能力需要显式的空间池化或更大分辨率**，
而不是更多 token。

## 3d. 换预训练 ViT 编码器：通用识图能力达标（2026-11-08，决定性）

第 3b 节确认瓶颈在视觉编码器。于是换掉 1.21M 的 CNN tower，改用
**timm （22M，ImageNet 预训练，196 patch token，
224px 输入）**，冻结 ViT 只训投影层（LLaVA 式）。

权重从 ModelScope 下载（HuggingFace 在本机不可达），150/150 张量全部加载。

### 三编码器横向对比（同数据、同 10 epoch）

| 能力 | CNN 48tok | CNN 192tok | **ViT 冻结** | **ViT 解冻顶部4块** |
|---|---|---|---|---|
| **spatial** | 0.275 | 1.000 | **1.000** | **1.000** |
| **scene** | 0.355 | 1.000 | **1.000** | **1.000** |
| **multi_attr** | 0.180 | 0.795 | **1.000** | **1.000** |
| **compare** | 0.170 | 0.450 | **0.900** | **0.995** |
| **count** | 0.240 | 0.280 | **0.825** | 0.815 |
| **attr** | 0.275 | 0.755 | 0.725 | **0.980** |
| **mean** | 0.249 | 0.713 | **0.917** | **0.965** |

### 三条结论

1. **预训练视觉编码器是决定性的。** 同样的 350M Jaume 骨干、同样的数据，
   换掉 CNN 后均值从 0.713 到 **0.965（解冻顶部 4 块）**，五项满分。
   这证明 **350M 文本骨干完全胜任通用识图**，之前的失败纯粹是编码器太弱。
2. **ViT 解冻少量顶层是性价比最高的配置。** 只解冻 4 个 block（约 8M 参数），
   attr 从 0.725 跃到 0.980，compare 从 0.900 到 0.995。
3. **CNN 与 ViT 的能力侧重不同。** CNN 在 spatial/scene 上的满分说明它擅长
   低级几何；但 count 只有 0.28，ViT 有 0.83。预训练视觉表征带来了
   物体级语义，这是从头训的小 CNN 学不到的。

### 对 UI/GUI 模型的直接指导

- **不要自己从头训视觉编码器。** 用 timm 预训练 ViT 起步，代价极低
  （22M 参数、ModelScope 6 秒下载）。
- **冻结 + 投影 + 解冻顶部几块** 是 61GB 显存下最稳的配方。
- UI 场景的额外难点会是小字号（需更高分辨率，如 448/512）和密集布局
  （需更多 token），但**骨干和桥接范式已被证明可用**。

## 3e. Google SigLIP 2：四个编码器的最终对比（2026-11-09）

SigLIP 2 是 Google 用 sigmoid 对比学习在图文对上训练的视觉塔，特征已经
和语言空间对齐，正是 VLM 桥接需要的性质。权重从 ModelScope 取
（，1.5GB，78 秒）。

> 注意：本机 torchaudio ABI 损坏，transformers 会在 import 时炸。
> 脚本在 import 前装了带  的 stub 模块绕过（不用音频，安全）。
> 另外该 checkpoint 的 config 是旧  格式，要用  加载
> 完整模型再取 。

### 四编码器横向对比（同数据、同 350M 骨干、同 10 epoch）

| 能力 | CNN 192tok | ViT 冻结 | ViT 顶4解冻 | **SigLIP2 冻结** | **SigLIP2 顶4解冻** |
|---|---|---|---|---|---|
| spatial | 1.000 | 1.000 | 1.000 | **1.000** | **1.000** |
| scene | 1.000 | 1.000 | 1.000 | **1.000** | **1.000** |
| multi_attr | 0.795 | 1.000 | 1.000 | **1.000** | **1.000** |
| compare | 0.450 | 0.900 | 0.995 | **0.965** | **0.985** |
| count | 0.280 | 0.825 | 0.815 | **0.960** | 0.955 |
| attr | 0.755 | 0.725 | 0.980 | 0.790 | 0.810 |
| **均值** | 0.713 | 0.917 | 0.965 | **0.953** | **0.958** |

### 结论

1. **SigLIP 2 是当前最优视觉塔。** 只冻结就有 0.953，而 ImageNet ViT
   冻结只有 0.917。图文对齐预训练带来的收益集中在**计数（0.825→0.960）
   和比较（0.900→0.965）**——恰恰是需要语义理解而非低级几何的能力。
2. **SigLIP2 上解冻顶层收益很小（0.953→0.958）。** 说明它给的特征已经足够好，
   不需要再适配。这对 UI 模型是好消息：**冻结即用，省显存省时间**。
3. **attr 在两个模型上都只有 0.79-0.81**，是全谱系唯一没满分的。
   该族混了 shape/color/size 三类问题，且小物体带网格背景引入捷径，
   属于任务设计问题，不是编码器问题。
4. **CNN 已经完全出局。** 计数 0.28 是硬伤，而 SigLIP2 是 0.96。

### 对 UI/GUI 模型的最终指导

- **视觉塔选 SigLIP 2，冻结使用。** 不需要解冻，不需要从头训。
- 61GB 显存下单卡跑 9000 样本 10 epoch 约 210s/epoch，完全够用。
- UI 的额外难点在分辨率（小字号）与 token 数（密集布局），
  属于工程参数，不是架构问题。

## 4. 下一步（按优先级）

| 实验 | 目的 | 判据 |
|---|---|---|
| **提高视觉 token 数**（48 → 144/256） | 验证容量假设 | mean 是否显著上升 |
| **全解冻 + 小学习率** | 验证冻结假设 | 是否稳定优于解冻 4 层 |
| **单任务训练**（只训 spatial） | 排除多任务干扰 | 能否接近 CNN 的 1.0 |
| 修 attr 的网格捷径 | 清洁 attr 任务 | CNN attr 是否能 > 0.8 |

如果提高 token 数后仍然不行，说明 **350M 文本编码器做通用视觉的容量不够**，
那就该考虑换 ViT 骨干（timm 已装）或加视觉专用层。

## 5. 对 UI/GUI 模型的启示

UI 理解比这里的基础识图**更难**（小字号文本、密集布局、精确坐标）。
如果连形状/颜色/空间关系都过不了桥接，UI 模型不能直接复用这个 350M 文本骨干，
需要独立的视觉编码器。这一点现在就可以确定，省掉后面一次错误投入。
